# 분석 흐름 (노드 기반 종목 분석) — 기능 검토

노드를 이어 붙여 `종목 가져오기 → 차트로 거르기 → AI 분석 → 결과 확인` 흐름을 만들고 실행하는 기능이다.
이 문서는 구현 전 검토 결과다. 결정이 필요한 항목은 마지막 절에 모았다.

## 1. 현재 데이터로 되는 것 / 안 되는 것 (2026-10-18 DB 기준)

| 항목 | 현재 상태 | 영향 |
|------|-----------|------|
| 주식 일봉(OHLCV) | AGE `(Stock)-[:HAS_PRICE]->(Price)`, open·high·low·close·volume·change_rate | 지표 계산에 필요한 필드는 다 있다 |
| 주식 일봉 기간 | **2026-09-30 ~ 2026-10-12, 7거래일** (백필 없음) | 이동평균·신고가·VCP·백테스트 모두 불가. **선행 작업 필요** |
| 종목 범위 | 비ETF Stock **559개** = ETF 구성종목(상위 30)에 한 번이라도 들어간 종목 | 시장 전체(약 2,700종목) 스크리너는 아니다 |
| 재무(PER·ROE·성장률) | 수집 안 함 | "대가 합의" 같은 재무 스크린 노드는 범위 밖 |
| 수급(외국인·기관) | 수집 안 함 | "큰손 추적" 노드는 범위 밖 |
| ETF 보유·비중 변화 | HOLDS, 액티브 ETF 비중 변화 | **이 앱만의 신호** — 노드로 쓸 수 있다 |
| LLM | LiteLLM 프록시 `qwen38-27b`, pydantic-ai (`services/answer/llm.py`) | AI 분석 노드에 그대로 재사용 |

### 선행 작업: 주식 일봉 백필

- `KISApiClient.get_daily_bars(code, start, end)`가 기간 조회·100건 페이지네이션을 이미 지원한다.
- 559종목 × 1년(약 250거래일) ≈ 종목당 3회 → 약 1,700회 호출. 0.06초 간격이면 2~3분.
- 일회성 백필 DAG(또는 `age_sync_universe`에 기간 인자)로 `collect_stock_prices_for_dates`를 재사용한다.
  `data-mapping.md`의 "백필 DAG는 없다" 원칙이 바뀌므로 문서도 같이 고친다.
- 이후 신규 편입 종목은 편입 시점에 과거 1년치를 함께 받아야 지표가 바로 나온다.

## 2. 노드 구성 (1차 범위)

각 노드는 `종목 집합 + 종목별 데이터`를 받아 `종목 집합 + 종목별 데이터`를 내보낸다.

| 단계 | 노드 | 설정 | 출력 |
|------|------|------|------|
| ① 가져오기 | 종목 가져오기 | 출처: ETF 보유 전체 / 특정 ETF 구성종목 / 내 포트폴리오 실보유(look-through) / 직접 입력 | 종목 목록 |
| ② 거르기 | 차트로 거르기 | 조건 여러 개 AND: 이평 정배열(5>20>60), N일 신고가 대비 −x% 이내, 거래량 20일 평균 대비 x배, 등락률 범위, 간이 VCP | 통과 종목 + 조건별 계산값 |
| ② 거르기 | ETF 신호로 거르기 | 담은 ETF 수 ≥ n, 최근 액티브 ETF 신규 편입/비중 증가 | 통과 종목 + 신호 |
| (합치기) | 교집합 / 합집합 | 입력 2개 이상 | 종목 목록 |
| ③ AI 분석 | AI 분석 | 최대 종목 수(기본 10), 관점(추세/위험/요약) | 종목별 근거 정리 텍스트 |
| ④ 결과 | 결과 확인 | 정렬 기준, 표시 열 | 비교 표 + 종목별 미니 차트 |

원칙 (챗봇과 동일): **숫자는 백엔드가 계산하고 LLM은 근거 정리만 한다.** AI 노드에는 계산된 지표와
ETF 편입 정보만 넘기고, 가격 예측·매수 권유 문구는 금지한다. 결과 화면에 "교육·연구용, 투자 권유 아님"을 표시한다.

백테스트·리스크 비중·대가 합의는 데이터(기간·재무) 확보 후 2차로 미룬다.

## 3. 구조

### 백엔드

```
backend/app/services/flow/
  nodes/            노드 1종 = 파일 1개 (params 스키마 + run)
    source.py  chart_filter.py  etf_signal.py  set_ops.py  ai_analysis.py  result.py
  registry.py       노드 카탈로그 (프론트 팔레트·설정 폼이 이걸로 그려진다)
  executor.py       위상 정렬 → 노드 순서 실행, 노드별 상태·건수 이벤트
  market_data.py    유니버스 OHLCV를 한 번에 읽어 실행 동안 캐시
backend/app/routers/flows.py
  GET  /flows/nodes          카탈로그
  CRUD /flows                사용자 흐름 저장 (JSON 그래프)
  POST /flows/{id}/run       SSE로 노드별 진행·결과 스트리밍 (챗봇 스트리밍과 같은 방식)
```

- 새 테이블 `analysis_flows(id, user_id, name, graph JSONB, created_at, updated_at)`. 실행 결과는 1차에선 저장하지 않는다.
- 지표 계산은 노드마다 Cypher를 돌리지 않고, 실행 시작 시 대상 종목의 OHLCV를 한 쿼리로 읽어 메모리에서 계산한다
  (559종목 × 250일 ≈ 14만 행). 느리면 RDB에 일봉 테이블을 두는 것을 검토한다.
- 노드 레지스트리 방식은 기존 답변 스킬(`services/answer/skills/base.py`)의 "파일 하나 = 기능 하나" 패턴을 따른다.

### 프론트엔드

- 새 페이지 `/flows`: 왼쪽 노드 팔레트(단계별 + 추천 조합), 가운데 캔버스, 오른쪽 `설정 / 결과` 탭.
- 캔버스는 `@xyflow/react`(React Flow) 추가를 제안한다. 노드마다 실행 후 `✓ 69종목` 같은 건수 배지를 붙인다.
- 결과 표·차트는 `components/answer`의 `DataTable`, `ChartView`(echarts)를 재사용한다.
- 추천 조합(템플릿)은 미리 만든 그래프 JSON을 불러오는 것으로 처리한다.

## 4. 위험·주의

- **데이터 기간**: 백필 전에는 기능이 사실상 동작하지 않는다. 1단계로 백필부터 한다.
- **유니버스 편향**: ETF가 담은 종목만 대상이라 대형주 위주다. 화면에 "ETF 편입 종목 559개 중" 처럼 범위를 밝힌다.
- **LLM 비용·시간**: 로컬 프록시라도 종목당 1회 호출이면 10종목에 수십 초. 상한·취소(stop 이벤트)를 둔다.
- **규제 문구**: 매매 판단·주문 노드는 만들지 않는다.

## 5. 결정이 필요한 것

1. 캔버스 방식 — 자유 그래프(React Flow, 분기·교집합 가능) vs 고정 4단계 파이프라인(구현 단순)
2. 백필 기간 — 1년(권장) / 6개월 / 2년
3. 흐름 저장 범위 — 개인 저장만 / 공유 포트폴리오처럼 공유까지
4. 1차에 "ETF 신호로 거르기" 노드 포함 여부 (권장: 포함 — 다른 스크리너와의 차별점)

## 6. 작업 순서 (제안)

1. 주식 일봉 1년 백필 DAG + 신규 편입 종목 과거치 수집
2. 백엔드: market_data · 노드 4종(가져오기·차트 거르기·교집합·결과) · executor · 라우터 · 테스트
3. 프론트: `/flows` 페이지, 캔버스, 설정/결과 패널
4. AI 분석 노드 + ETF 신호 노드
5. 추천 조합 템플릿, 문서(README·Architecture 페이지) 갱신
