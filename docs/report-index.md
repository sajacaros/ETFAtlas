# 정기보고서 색인: 목차 트리 (PageIndex 방식)

챗봇이 정기보고서(사업·반기·분기보고서)에 적힌 사실을 답하는 방식. 보고서를 미리 목차 트리로 색인해 두고,
질문이 오면 LLM이 목차를 보고 답이 있는 절을 골라 그 절만 읽는다. [PageIndex](https://github.com/VectifyAI/PageIndex)의
방식(트리 + 노드 요약 + 추론으로 고르기 + 절 단위 출처)을 따르되, 패키지는 쓰지 않고 직접 구현했다.

| 구성 | 위치 |
|---|---|
| 파서·렌더링·노드 요약 프롬프트 (stdlib만, Airflow와 백엔드가 같이 import) | `backend/app/services/report_tree.py` |
| 색인 DAG | `airflow/dags/dart_report_index.py` ([dags.md](dags.md#7-dart_report_index-rdb-llm)) |
| 스킬 | `company_report`, `company_revenue_mix` ([answer-skills.md](answer-skills.md#등록된-스킬)) |
| 테이블 | `stock_reports`, `stock_report_docs`, `report_nodes` (마이그레이션 0033) |

## 왜 패키지를 쓰지 않았나

- PageIndex 공개 버전은 텍스트 PDF만 받는다. DART가 주는 원문은 XML이다.
- PageIndex에서 가장 비싼 단계는 문서 레이아웃으로 목차를 추정하는 것인데, DART 원문은 장·절을 `SECTION-1/2/3`으로 감싸고
  제목에 `ATOC="Y"`·`ATOCID`를 단다. 목차를 규칙으로 정확히 만들 수 있다.
- 모델 연결이 OpenAI 키 또는 Claude Code 구독 방식이라 관리자 페이지에서 등록한 LLM(`ai_settings`)과 맞지 않는다.

## 이전 방식의 한계 (0032까지)

`company_report`는 처음 물을 때 II·IV·XI장과 '영업부문' 주석만 장당 6천 자·합계 3.6만 자로 잘라 고정된 4항목 요약 하나를 남겼다.
삼성전자 반기보고서 기준 원문 70만 자의 4%만 읽었고,
- 요약 틀 밖의 질문(연구개발비, 직원, 최대주주, 배당, 감사의견 …)에 답할 수 없었고,
- 주석 이름이 '부문별 보고 (연결)'인 회사의 부문 표를 놓쳤고,
- 합계 상한에 걸려 XI.3 제재·XI.4 기준일 이후 주요사항이 잘렸고,
- 여러 줄 표 머리말이 한 줄로 펴져 3개월·누적 열이 섞였다.

## 저장: 세 층

텍스트로 펴서 저장하지 않는다. 원문 → 구조 → 색인으로 나눠 두고, LLM에 넘길 때만 마크다운으로 렌더링한다.

1. **원문** `stock_report_docs`: DART `document.xml` zip 그대로 (보고서당 0.35~0.8MB). 파서를 고치면 DART를 다시 부르지 않고
   이것으로 트리를 다시 만든다 (`PARSER_VERSION`을 올리면 DAG가 다시 만든다).
2. **구조** `report_nodes`: 노드 = 장·절·주석. 본문은 노드의 `blocks`(JSON)에 둔다.
   - `heading`: '가.', '(1)', '1)', '[표 제목]' 같은 소제목 줄
   - `para`: 문단
   - `table`: `{caption, unit, header, rows}`. 병합 셀을 푼다 — `ROWSPAN`은 아래 행에 같은 값을 채워 행만 떼어 읽어도 뜻이 통하게,
     본문의 `COLSPAN`은 빈 칸. 여러 줄 머리말은 열마다 아래 세 단계를 ' / '로 잇는다 (`보고부문 / DX 부문 / 3개월`).
     표 바로 위의 작은 표(`[연구개발비용] | (단위 : 백만원, %)`)는 다음 표의 캡션·단위가 된다. 주석의 '표를 담은 틀 표'(XBRL 서식)는
     틀을 벗기고 안의 표를 읽는다. 한 칸짜리 표는 문단으로 둔다.
   - 블록을 행으로 나누지 않고 노드에 JSON으로 두는 것은 읽을 때 늘 노드 단위로 읽기 때문이다 (보고서당 200행 안팎).
3. **색인** `report_nodes.summary`: 노드에 든 항목을 등록된 LLM이 한 줄로 적은 것 (예: `연구개발비용 총계, 매출액 대비 연구개발비 비율,
   부문별 주요 연구개발 실적`). 답이 아니라 고르기용이다. `content_hash`(경로 + 본문)가 같으면 다시 요약하지 않는다.

### 노드 나누기

- 노드 본문은 다음 제목 전까지이고 하위 노드 본문은 들어가지 않는다. 같은 SECTION 안의 다음 제목(주석 항목)은 그 SECTION 노드의 자식.
- 8천 자가 넘는 절은 '가.' 소제목마다 하위 노드로 나눈다 (`27` → `27-1` … `27-7`). 'VIII.1 임원 및 직원 등의 현황'(11.8만 자)이
  '마. 직원 등의 현황'(1천 자) 같은 하위 노드가 돼 목차에서 바로 고를 수 있다.
- 그래도 큰 노드는 거대한 표다 (미등기임원 명단 1,108행). 읽을 때 큰 표는 앞 3행·합계 행·질문 키워드가 든 행만 넣고 몇 행 중 몇 행인지 밝힌다.

## 색인 (DAG)

`queue_reports → build_trees → summarize_nodes → prune_reports`, 매일 21:00. 자세한 것은 [dags.md](dags.md#7-dart_report_index-rdb-llm).

- 범위: 그래프 종목의 최근 1년 정기보고서(4~5건). 같은 기간이면 정정본만, 1년 지나면 지우되 종목마다 최신 1건은 남긴다.
- 상태: `pending` → `tree`(트리만, 제목으로 고른다) → `summarized` | `failed`.
- 노드 요약: 등록된 LLM, **추론을 끈다** (`chat_template_kwargs.enable_thinking=False` — 켜 두면 노드 하나에 2분을 넘긴다).
  100자 미만 노드, 재무제표 본표(2-1. 연결 재무상태표 …), XII 상세표는 제목으로 충분해 요약하지 않는다.
  긴 노드는 본문 앞부분만 넣으면 뒤쪽 항목이 색인에서 빠지므로(직원 현황이 빠졌었다), 노드 전체의 소제목·표 제목 목록을 먼저 넣는다.
- 비용: 삼성전자 보고서 1건 = 노드 130~160개, 입력 약 20만 토큰, 동시 4개로 약 1분. 처음 색인은 종목 수 × 4~5건이라 실행당 시간 예산
  (트리 90분, 요약 240분) 안에서 종목별 최신 보고서부터 며칠에 나눠 끝난다.
- 공간: 보고서당 약 1.1MB (원문 zip + 노드, TOAST 압축 후).

## 읽기 (스킬)

`company_report(stock, need?, period?)`
- `need`가 있으면: 목차(들여쓰기 + `[id] 제목 (글자 수) — 요약`, 짧은 빈 서식 노드는 뺀다)와 찾을 것·질문을 주고 노드 1~3개와
  표 행 키워드를 고르게 한다 (구조화 출력, temperature 0). 목차에 없는 id만 고르면 한 번 더 묻는다. 본문이 없는 장을 고르면 하위 절을 읽는다.
  고른 노드를 노드당 1.2만 자·합계 3만 자로 렌더링해 답하고, 답 머리에 읽은 절과 DART 원문 링크를 붙인다.
  절 id는 답에 따라 나오므로 읽은 절에는 경로만 넣는다.
- `need`가 없으면: 개요. II·IV·XI장의 모든 절과 부문 주석을 절마다 몫(1.5천~5천 자, 합계 4.8만 자)을 나눠 읽고 4항목으로 요약한다.
- `company_revenue_mix`와 개요의 매출 구성 차트는 매출 표 절과 부문 주석(제목에 '부문', 연결 우선)의 표를 렌더링해 `report_breakdowns`에
  넘긴다. 옮긴 값은 그 렌더링 결과에 그대로 있는지 검사한다.
- 개요와 매출 구성은 보고서마다 한 번 만들어 `stock_reports.overview`·`breakdowns`에 남긴다.

## 측정 (삼성전자 2026 반기·2025 사업보고서, 등록 LLM)

질문 24개(연구개발비, 최대주주, 배당, 부문 영업이익, 직원, 소송, 원재료, 환율, 자기주식, 종속회사, 재고, 감사의견, 시설투자, 가동률,
사외이사, 임원 보수, 제재, 매출처, 시장점유율, 사업목적, 대손충당금, 수주, 신용등급, 주총). 정답 절은 원문을 직접 찾아 정했다.

| 목차에 넣은 것 | 기존 12문항 | 새 12문항 |
|---|---|---|
| 제목만 | 11/12 · 11/12 | 8/12 · 8/12 |
| 제목 + 노드 요약 | 12/12 · 12/12 | 12/12 · 12/12 |

제목만으로 틀린 것은 답이 제목으로 짐작하기 어려운 절에 있던 경우다 (연구개발비 비율 → '주요계약 및 연구개발활동', 신용등급 → '회사의 개요',
대손충당금 → '기타 재무에 관한 사항'). 스킬 전체(트리 → 요약 → 고르기 → 답)를 임시 DB에서 돌렸을 때도 24문항 모두 정답 절을 읽었고,
답의 수치(연구개발비 비율 9.0%, 직원 129,200명·1인 평균급여 63백만원, 부문별 영업이익, 자기주식 82,086,705주, 가동률 등)는 원문과 같았다.
질문당 3~9초.

## 바꿀 때

- 파서를 바꾸면 `PARSER_VERSION`을 올린다. 다음 DAG 실행이 보관한 원문으로 트리를 다시 만들고, 내용이 바뀐 노드만 다시 요약한다.
- 요약 프롬프트(`SUMMARY_PROMPT`)를 바꿔 전부 다시 요약하려면 `UPDATE report_nodes SET summary = NULL; UPDATE stock_reports SET status = 'tree' WHERE status = 'summarized';`
- 개요 프롬프트를 바꾸면 `UPDATE stock_reports SET overview = NULL`, 매출 구성 추출을 바꾸면 `breakdowns = NULL`.
