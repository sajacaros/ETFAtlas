ETF Atlas 발표 스크립트
- Apache AGE, LLM 에이전트, Airflow로 만든 ETF 정보 서비스 적용기

========================================
오프닝
========================================

안녕하세요. 오늘은 기술 리서치 프로젝트로 진행한 ETF Atlas를 소개하면서,
그 과정에서 사용한 기술과 부딪힌 문제들을 이야기하려 합니다.

--- 문제 제기 ---

본격적인 기술 소개에 앞서, 왜 이런 기술이 필요했는지부터 짚어보겠습니다.

한국 증시에 상장된 ETF는 약 1,175개입니다.
그중 국내 주식형이면서 순자산 500억 원 이상인 것만 골라도 190개,
순자산 합계로 약 156조 원입니다.
이 ETF들이 담은 종목을 이으면 보유 관계만 수천 건이 됩니다.
이 데이터에서 의미 있는 정보를 뽑으려면 관계를 탐색해야 합니다.

예를 들어 "삼성전자를 가장 많이 보유한 ETF는?"이라는 질문은
관계형 DB라면 JOIN 여러 개에 GROUP BY, ORDER BY를 써야 합니다.
"KODEX 200과 비슷한 ETF는?"은 자기 조인에 집계까지 겹칩니다.
쿼리가 복잡해질수록 성능과 가독성이 함께 떨어집니다.

거기에 욕심을 하나 더 냈습니다.
이런 질문을 개발자가 아닌 사람도 할 수 있으면 어떨까?
"삼성전자와 SK하이닉스가 많이 든 ETF를 수수료순으로 보여줘"라고 자연어로 물으면
알아서 데이터를 찾아 답해주는 챗봇을 만들고 싶었습니다.

복잡한 관계 탐색, 자연어 질의, 그리고 매일 쌓이는 시장 데이터의 자동 수집.
이 세 가지를 풀려고 고른 기술이
Apache AGE, LLM 에이전트 프레임워크, Apache Airflow입니다.

--- 기술 선택 배경 ---

주제는 평소 관심 있던 ETF 투자로 잡았습니다.
실제 서비스에 가까운 도메인에서 써 봐야
리서치 결과가 의미 있다고 생각했기 때문입니다.

첫 번째는 그래프 데이터베이스입니다.
ETF 데이터는 본질적으로 관계 중심입니다.
ETF가 종목을 보유하고, 그 종목이 또 다른 ETF에 들어 있고, ETF에는 테마가 붙습니다.
이런 관계는 그래프로 표현하는 게 자연스럽습니다.
별도의 그래프 DB 서버를 띄우는 대신
PostgreSQL 확장으로 동작하는 Apache AGE를 골랐습니다.

두 번째는 LLM 에이전트입니다.
처음에는 Hugging Face의 경량 프레임워크인 smolagents, 그중에서도 CodeAgent로 시작했습니다.
지금은 pydantic-ai 기반의 tool-calling 에이전트로 바꿨습니다.
왜 바꿨는지가 오늘 이야기의 한 축입니다.

세 번째는 데이터 파이프라인입니다.
매일 시장 데이터를 수집하고, 가공하고, 적재해야 하는데,
배치 중심 워크로드에 Python 네이티브인 Apache Airflow를 선택했습니다.
지금은 3.x 버전을 쓰고 있습니다.

데이터 소스는 한국투자증권 KIS Open API로 통일했습니다.
초기에는 KRX Open API와 pykrx를 같이 썼는데, 지금은 모두 걷어냈습니다.

이 기술들이 실제 서비스 수준의 프로젝트에서 얼마나 쓸 만한지,
그리고 쓰다 보니 무엇을 바꾸게 됐는지를 순서대로 공유하겠습니다.


========================================
Apache AGE 기술 소개
========================================

--- Apache AGE란? ---

Apache AGE는 PostgreSQL에 그래프 데이터베이스 기능을 더하는 확장(Extension)입니다.
이름 자체가 "A Graph Extension"의 약자입니다.
이 프로젝트에서는 PostgreSQL 18 위에 AGE 1.8.0을 올려 씁니다.

핵심 특징은 세 가지입니다.
첫째, PostgreSQL 위에서 동작합니다. 별도 DB 서버 없이 확장만 설치하면 됩니다.
둘째, Cypher 쿼리를 지원합니다. Neo4j에서 쓰던 Cypher 문법을 대부분 그대로 쓸 수 있습니다.
셋째, SQL과 Cypher를 함께 쓸 수 있습니다.
관계형 테이블, 그래프, 그리고 pgvector 임베딩까지 한 DB에 둘 수 있다는 게 큰 장점입니다.

라이선스는 Apache 2.0입니다.

--- Neo4j vs Apache AGE ---

Neo4j와 비교해 보겠습니다.

Neo4j는 전용 그래프 DB입니다. 성능과 기능 면에서 가장 성숙합니다.
다만 Community와 Enterprise 에디션으로 나뉘고 Enterprise는 상용 라이선스입니다.
별도 서버를 운영해야 하고, 기존 RDBMS와 데이터를 따로 관리해야 합니다.

Apache AGE는 PostgreSQL 확장입니다.
기존 PostgreSQL 인프라를 그대로 쓰면서 그래프 기능을 더합니다.
대신 Cypher 지원이 완전하지 않고, 에코시스템이 작습니다.

정리하면, 이미 PostgreSQL을 쓰고 있고
그래프 쿼리가 워크로드의 일부라면 AGE가 합리적인 선택입니다.

--- AGE 동작 방식 ---

AGE에서는 일반 SQL 안에서 cypher() 함수를 호출합니다.

  SELECT * FROM cypher('etf_graph', $$
      MATCH (e:ETF {code: '069500'})-[h:CURRENT_HOLDS]->(s:Stock)
      RETURN {stock: s.name, weight: h.weight}
      ORDER BY h.weight DESC LIMIT 10
  $$) as (result agtype);

KODEX 200의 현재 보유종목 상위 10개를 가져오는 쿼리입니다.

주의할 점이 몇 가지 있습니다.
그래프 이름, 여기서는 'etf_graph'를 지정해야 합니다.
결과 타입은 agtype이라는 AGE 전용 타입입니다.
그리고 반환 컬럼을 하나로 선언했기 때문에,
값을 여러 개 돌려줄 때는 {key: value} 맵으로 감싸서 내보내야 합니다.

--- 써 보며 만난 AGE의 특성 ---

실제로 쓰면서 부딪힌 것도 몇 가지 말씀드리겠습니다.

첫째, 같은 WITH 절에서 만든 별칭으로는 ORDER BY를 할 수 없습니다.
집계한 값으로 정렬하려면 WITH를 한 번 더 둬야 합니다.

둘째, Cypher 쿼리가 SQL의 $$ ... $$ 따옴표 안에 들어갑니다.
그래서 쿼리 안에 $$가 섞이면 따옴표가 닫히고, 그 뒤가 날 SQL로 해석됩니다.
평소에는 문제가 안 되지만, LLM이 쓴 쿼리를 실행할 때는 아주 중요한 문제가 됩니다.
챗봇 이야기에서 다시 다루겠습니다.

셋째, MERGE 뒤에 SET을 붙이는 패턴에 버그가 있어서,
가격 노드는 "없으면 CREATE, 있으면 SET" 두 단계로 나눠 저장합니다.


========================================
LLM 에이전트 프레임워크 — smolagents에서 pydantic-ai로
========================================

--- 에이전트가 도구를 부르는 두 가지 방식 ---

LLM 에이전트는 반복 구조입니다.
모델이 "어떤 도구를 어떤 인자로 부를지" 정하면,
프로그램이 그 도구를 실행하고 결과를 다시 모델에 돌려줍니다.
모델이 도구 없이 답을 내면 끝납니다.

도구를 부르는 방식은 크게 둘로 나뉩니다.

하나는 코드 생성 방식입니다. smolagents의 CodeAgent가 대표적입니다.
LLM이 Python 코드를 쓰고, 그 코드 안에서 도구 함수를 호출합니다.
변수에 값을 담고, for 루프를 돌고, 조건 분기를 할 수 있어서 유연합니다.
대신 LLM이 만든 코드를 백엔드 프로세스에서 실행해야 합니다.

다른 하나는 tool calling 방식입니다. 지금 쓰는 pydantic-ai가 여기 해당합니다.
LLM이 JSON 인자로 도구를 호출합니다.
인자는 JSON 스키마로 검증되고, 틀리면 재시도 프롬프트로 모델에 되돌아갑니다.
실행되는 코드는 우리가 직접 작성한 도구뿐입니다.

--- smolagents — 처음의 선택 ---

smolagents는 Hugging Face가 만든 경량 에이전트 프레임워크입니다.
철학은 "최소한의 추상화"입니다.
LangChain이 무겁게 느껴져서 골랐고,
Model, Tool, Agent 세 가지만 알면 바로 시작할 수 있었습니다.
CodeAgent는 도구 호출을 Python 코드로 생성하는데,
처음에는 이 유연함이 큰 장점으로 보였습니다.

--- pydantic-ai — 지금의 선택 ---

프로젝트를 재가동하면서 세 후보를 다시 비교했습니다.

smolagents를 유지하는 방법이 있었습니다.
익숙하지만, LLM이 만든 코드를 실행한다는 구조는 그대로 남습니다.

LangChain의 deepagents도 봤습니다.
계획(todo), 가상 파일시스템, 서브에이전트 같은 장기 작업용 기능이 중심인데,
도구 10개로 몇 단계면 끝나는 이 챗봇에는 과했습니다.

마지막이 pydantic-ai였습니다.
가볍고, OpenAI 호환 엔드포인트를 그대로 쓸 수 있고,
도구 인자를 스키마로 검증해 주고, 무엇보다 코드 실행이 없습니다.
그래서 pydantic-ai를 골랐습니다.

결정적인 이유는 보안이었습니다.
smolagents의 로컬 Python 실행기는 샌드박스가 아니었습니다.
그리고 돌이켜 보면 우리 챗봇에 필요한 건 "코드 실행"이 아니라
"읽기 전용 조회 도구를 순서대로 부르는 것"이었습니다.

전환 비용도 생각보다 작았습니다.
pydantic-ai의 run_stream_events가 도구 호출과 결과를 이벤트로 흘려 주는데,
이걸 프론트엔드가 원래 받던 단계(step) 이벤트로 바꿔 주기만 하면 됐습니다.
SSE 형식을 바꾸지 않았기 때문에 프론트엔드는 손대지 않았습니다.


========================================
Apache Airflow 기술 소개
========================================

--- Apache Airflow란? ---

Apache Airflow는 데이터 파이프라인을 작성하고, 스케줄링하고, 모니터링하는 플랫폼입니다.
Airbnb에서 시작했고, 지금은 Apache 최상위 프로젝트입니다.

핵심 개념은 네 가지입니다.

첫째, DAG입니다.
Directed Acyclic Graph, 방향이 있고 순환이 없는 그래프라는 뜻인데,
쉽게 말하면 작업 흐름을 Python 코드로 정의한 것입니다.

둘째, Task입니다.
DAG 안에서 실행되는 개별 작업 단위입니다.
"유니버스 수집", "구성종목 수집", "수익률 계산" 같은 것들이 각각 Task입니다.

셋째, Operator입니다.
Task가 무엇을 할지 정하는 템플릿입니다.
Python 함수를 실행하는 PythonOperator,
조건이 맞지 않으면 이후 Task를 건너뛰는 ShortCircuitOperator 같은 것들이 있습니다.

넷째, Scheduler입니다.
"화요일부터 토요일 아침 8시 반"처럼 정한 주기에 맞춰 DAG를 실행하는 엔진입니다.

--- Airflow 3.x 구성 ---

지금은 Airflow 3.3.2를 Python 3.14 기반 커스텀 이미지로 씁니다.

2.x 때는 웹서버와 스케줄러를 컨테이너 하나에서 같이 돌렸는데,
3.x에서는 역할이 나뉩니다.
웹 UI와 API를 맡는 api-server,
실행 시점을 판단하고 Task를 돌리는 scheduler(LocalExecutor),
DAG 파일을 파싱하는 dag-processor,
그리고 메타데이터 DB 마이그레이션과 초기 설정을 하는 airflow-init입니다.

코드 쪽에서도 import 경로가 바뀌었습니다.
DAG는 airflow.sdk에서, 표준 오퍼레이터는 airflow.providers.standard에서 가져옵니다.

--- 왜 Airflow를 선택했나 — NiFi와의 비교 ---

비교 대상으로 NiFi를 봤습니다.

NiFi는 실시간 데이터 라우팅에 초점을 둡니다.
웹 브라우저에서 드래그 앤 드롭으로 플로우를 만들고,
IoT 센서 데이터, 로그 수집, 시스템 간 실시간 전달에 강합니다.

Airflow는 배치 작업 오케스트레이션에 초점을 둡니다.
정해진 시간에 작업을 실행하고, 작업 간 의존 관계를 관리합니다.
워크플로가 Python 코드라서 Git으로 버전 관리하고 리뷰할 수 있습니다.

ETF Atlas의 요구사항은 이렇습니다.
"거래일 다음 날 아침, KIS Open API에서 전날 확정된 데이터를 가져와 가공해 그래프에 적재한다."
전형적인 배치 작업입니다.
게다가 수집 로직이 KIS API 클라이언트 같은 Python 코드라서
Python 네이티브인 Airflow가 자연스러웠습니다.


========================================
프로젝트 개요 & 아키텍처
========================================

--- 프로젝트 개요 ---

ETF Atlas는 한국 ETF 정보를 수집·분석하고, AI 챗봇으로 질의하는 웹 서비스입니다.

주요 기능은 다섯 가지입니다.
하나, ETF 탐색 — 검색, 테마 태그별 조회, 보유종목, 유사 ETF
둘, 워치리스트 — 관심 ETF의 보유종목 비중 변화 추적과 알림
셋, 포트폴리오 — 매수 기록, 목표 비중, 일별 스냅샷 대시보드
넷, AI 챗봇 — 자연어로 ETF 데이터 질의
다섯, 관리자 — 챗봇 로그 승인, ETF 태그 수동 지정

--- 전체 아키텍처 ---

전체는 Docker Compose로 띄웁니다.

- db: PostgreSQL 18 + Apache AGE 1.8.0 + pgvector + pg_trgm
- backend: FastAPI (Python 3.14) + pydantic-ai
- frontend: React 18 + TypeScript + Vite. nginx가 정적 파일을 서빙하고 /api를 백엔드로 넘깁니다
- airflow: 3.3.2, api-server / scheduler / dag-processor / airflow-init

하나의 PostgreSQL에 관계형 테이블, AGE 그래프, pgvector 임베딩이 함께 들어 있습니다.
사용자와 포트폴리오 같은 CRUD는 관계형 테이블,
ETF와 종목의 관계, 가격, 태그 같은 관계 탐색은 그래프,
챗봇의 예시 검색은 벡터입니다.
별도 서버 없이 한 DB에서 세 가지를 쓸 수 있다는 게 AGE를 고른 가장 큰 이유였습니다.

--- 운영 측면의 정리 ---

운영 쪽에서 정리한 것도 세 가지 말씀드리겠습니다.

첫째, 외부에 열린 포트는 프론트엔드(9600) 하나입니다.
백엔드, DB, Airflow 포트는 모두 127.0.0.1에만 바인딩했습니다.
외부 요청은 nginx가 /api로 받아서 내부망으로 넘기고,
서버에 있는 Airflow UI는 SSH 터널로 엽니다.
Docker의 포트 공개가 호스트 방화벽 규칙을 우회할 수 있다는 점 때문에 내린 결정입니다.

둘째, 인증은 ID와 비밀번호로 바꿨습니다.
예전에 쓰던 Google OAuth는 걷어냈습니다.
사용자가 한 명도 없으면 첫 화면이 /setup 페이지로 가고,
거기서 만든 계정이 관리자가 됩니다.

셋째, 관계형 스키마는 Alembic으로 관리합니다.
기존 init SQL은 동결된 기준 리비전(0001)으로 두고,
백엔드 컨테이너가 기동할 때 alembic upgrade head를 실행합니다.
그래서 새로 만든 DB든 기존 DB든 같은 상태에 도달합니다.
0002 리비전에서는 포트폴리오 관련 외래키에 NOT NULL을 추가했습니다.


========================================
데이터 수집 — KIS Open API & Airflow
========================================

--- 데이터 소스: KIS 하나로 ---

시장 데이터는 한국투자증권 KIS Open API로 통일했습니다.
키 하나로 필요한 대부분을 얻습니다.

- ETF 목록: 공개 종목 마스터 파일(kospi_code.mst)의 ETF 그룹. 인증도 필요 없습니다
- ETF/ETN 현재가: NAV, 순자산, 상장주식수
- 국내주식 기간별 시세: 일봉입니다. ETF와 주식 가격, 그리고 영업일 목록에 씁니다.
  영업일은 KODEX 200의 일봉 날짜로 판단합니다
- ETF 구성종목 시세: 보유종목과 비중
- 국내휴장일조회: 오늘 장이 열리는지. 하루 한 번만 조회해서 캐시합니다

KIS가 ETF 총보수를 주지 않아서 보수율만 네이버 증권에서 가져옵니다.
그리고 솔직히 말씀드리면, 포트폴리오 현재가를 장중에 갱신하는 부분은 아직 yfinance를 씁니다.
이것까지 KIS 현재가로 옮기는 게 남은 과제입니다.

--- 유니버스 — 190개 ETF ---

어떤 ETF를 다룰지, 유니버스는 이렇게 정합니다.

상장 ETF 약 1,175개에서 시작합니다.
먼저 이름으로 거릅니다.
레버리지, 인버스, 선물, 합성, 커버드콜,
채권과 금리, 금·은·원자재, 통화, 머니마켓, 리츠,
그리고 해외에 투자하는 ETF를 뺍니다.
그러면 380여 개가 남습니다.
여기서 순자산 500억 원 이상만 남기면 190개, 순자산 합계 약 156조 원입니다.

한 번 유니버스에 들어온 ETF는 빠지지 않습니다.
운용사는 ETF 이름 앞의 브랜드, KODEX, TIGER, ACE 같은 걸로 판별해서
MANAGED_BY 관계로 연결합니다.

--- 수집 원칙 세 가지 ---

수집에는 원칙이 세 가지 있습니다.

첫째, 백필하지 않습니다.
첫 실행은 가장 최근 확정된 거래일 하루만 수집하고, 그 뒤로 매일 쌓습니다.
사실 선택의 여지도 없었습니다.
KIS 구성종목 API는 날짜를 지정할 수 없어서, 과거 보유종목은 애초에 얻을 수 없습니다.
그래서 1주, 1개월 수익률이나 비중 변화는 데이터가 쌓인 만큼만 보입니다.

둘째, 종가가 확정된 날까지만 수집합니다.
16시(KST) 전에 실행되면 전날까지만 수집합니다.
장중에 일봉을 요청하면 아직 끝나지 않은 당일 봉이 오기 때문입니다.
이건 실제로 사고가 난 뒤에 생긴 원칙인데, 시행착오 챕터에서 자세히 말씀드리겠습니다.

셋째, 구성종목은 비중 상위 30개만 저장합니다.
KIS 구성종목 API가 상위 30개만 돌려주고, 다음 페이지를 요청해도 같은 30개가 옵니다.
KODEX 200이라면 202종목 중 30개, 비중 합으로 약 85%입니다.
처음엔 고민했지만 그대로 받아들였습니다.
구성종목 데이터의 용도가 "XX와 YY가 많이 든 ETF를 수수료순으로" 같은 챗봇 질의이지,
운용사 장부와 정확히 맞춰 보는 게 아니기 때문입니다.

--- Airflow DAG 5개 ---

지금 운영하는 DAG는 다섯 개입니다.

첫 번째, age_sync_universe입니다. 화요일부터 토요일, 아침 8시 30분에 돕니다.
거래일 다음 날 아침에 전날 데이터를 수집하는 메인 DAG입니다.
거래일 목록을 구하고,
유니버스와 가격을 갱신하고,
구성종목을 수집하면서 CURRENT_HOLDS를 교체하고,
주식 가격과 수익률을 계산하고,
새로 들어온 ETF에는 규칙 기반 태그를 붙이고,
마지막으로 수집 완료를 기록하고 알림을 보냅니다.

두 번째, rdb_sync_metadata입니다. 평일 아침 8시 30분에 돕니다.
종목 마스터 파일에서 ETF 코드와 이름을 받아 관계형 etfs 테이블에 동기화하는 가벼운 DAG입니다.

세 번째, rdb_realtime_prices입니다. 평일 장중에 10분마다 돕니다.
첫 Task가 ShortCircuitOperator로 "지금 수집할 필요가 있나?"를 판단합니다.
오늘이 휴장일이면 건너뛰고,
장 마감 이후에 이미 한 번 수집했으면 건너뜁니다.
조건을 통과하면 포트폴리오에 담긴 티커의 현재가를 수집하고, 바로 이어서 스냅샷을 갱신합니다.

네 번째, age_tagging입니다. 토요일 새벽 3시에 돕니다.
새로 들어온 ETF에 테마 태그를 붙입니다. 규칙과 LLM을 같이 씁니다.

다섯 번째, embed_code_examples입니다. 수동으로 실행합니다.
챗봇이 참고할 예시의 질문을 일반화하고 임베딩해서 pgvector에 저장합니다.

--- Airflow에서 유용했던 기능 ---

써 보면서 특히 유용했던 기능을 꼽아 보겠습니다.

첫째, Configuration as Code입니다.
DAG가 Python 파일이니 Git으로 관리하고,
KIS 클라이언트 같은 수집 코드에는 단위 테스트도 붙일 수 있었습니다.

둘째, XCom입니다.
"거래일 목록" Task가 날짜 리스트를 반환하면 이후 Task들이 그걸 받아 씁니다.
Task를 독립적으로 유지하면서 데이터를 주고받을 수 있습니다.

셋째, 의존성과 병렬 실행입니다.
메인 DAG에서 유니버스 수집이 끝나면
구성종목, 수익률, 태그가 갈라져서 병렬로 돕니다.

넷째, 자동 재시도입니다.
retries=3, retry_delay 5분만 설정하면 API가 간헐적으로 실패해도 알아서 다시 시도합니다.
cron이었다면 실패 감지와 재시도를 다 직접 짜야 했을 겁니다.

다섯째, Params입니다.
태깅 DAG의 full_rebuild처럼, 수동으로 실행할 때 동작을 바꾸는 인자를 UI에서 넘길 수 있습니다.


========================================
그래프 데이터 활용
========================================

--- 그래프 모델 ---

그래프 이름은 etf_graph입니다.

노드는 여섯 종류입니다.
- ETF: 코드, 이름, 순자산, 보수율, 수익률
- Stock: 종목 코드와 이름
- Price: 일자별 시가/고가/저가/종가/거래량 등
- Company: 운용사
- Tag: 테마 태그
- User: 사용자(워치리스트용)

관계는 이렇습니다.
- HOLDS {date, weight, shares}: 날짜별 보유 이력. 변화 비교에만 씁니다
- CURRENT_HOLDS {date, weight, shares}: ETF별 현재 보유종목, 최대 30개. 수집할 때마다 교체됩니다
- HAS_PRICE: ETF와 종목의 가격 이력
- MANAGED_BY: 운용사
- TAGGED: 테마 분류
- WATCHES: 사용자의 관심 ETF

이 모델의 장점은 관계 탐색이 직관적이라는 겁니다.
"삼성전자를 보유한 ETF 중 반도체 태그가 달린 것" 같은 질의가 MATCH 패턴 하나로 표현됩니다.

--- 왜 CURRENT_HOLDS를 따로 두었나 ---

HOLDS와 CURRENT_HOLDS가 왜 둘 다 있는지 궁금하실 겁니다.

HOLDS는 ETF-종목-날짜마다 엣지가 하나씩 생깁니다.
거래일마다 약 4,100개, 1년이면 약 100만 개가 쌓입니다.

예전에는 "현재 보유종목"을 이렇게 구했습니다.

  MATCH (e:ETF)-[h:HOLDS]->(s:Stock)
  WITH e, s, h ORDER BY h.date DESC
  WITH e, s, head(collect(h)) AS latest
  ...

날짜 내림차순으로 정렬해서 첫 번째 것을 집는 방식인데,
ETF마다 이력 전체를 훑는 쿼리입니다. 데이터가 쌓일수록 느려집니다.

그래서 수집 직후에 그날의 HOLDS를 CURRENT_HOLDS로 복사해 두도록 바꿨습니다.
현재 보유종목 조회는 이제 ETF당 30개 이하의 엣지만 읽습니다.
KIS 조회에 실패한 ETF는 이전 구성종목을 그대로 유지하고,
같은 날짜로 다시 돌려도 결과가 같게 만들었습니다.

--- 유사 ETF ---

실제로 쓰는 쿼리 하나를 보겠습니다. 유사 ETF 찾기입니다.

  MATCH (e1:ETF {code: $etf_code})-[h1:CURRENT_HOLDS]->(s:Stock)
        <-[h2:CURRENT_HOLDS]-(e2:ETF)
  WHERE e1 <> e2
  WITH e2, COUNT(s) AS overlap,
       SUM(CASE WHEN h1.weight < h2.weight THEN h1.weight ELSE h2.weight END) AS similarity
  WHERE overlap >= $min_overlap
  RETURN {etf_code: e2.code, name: e2.name, overlap: overlap, similarity: similarity}
  ORDER BY similarity DESC LIMIT 5

두 ETF가 공통으로 가진 종목마다 비중의 작은 쪽을 더합니다.
단순히 겹치는 종목 수가 아니라 비중까지 반영하니, 실제로 구성이 비슷한 ETF가 나옵니다.

그리고 이 값을 기준 ETF의 비중 합으로 나눠 정규화합니다.
구성종목이 상위 30개뿐이라 비중 합이 100%가 아닌 ETF가 많기 때문입니다.
정규화하지 않으면 종목 수가 많은 지수형 ETF끼리의 유사도가 실제보다 낮게 나옵니다.

관계형 DB였다면 자기 조인과 집계가 얽힐 쿼리가,
그래프에서는 MATCH 패턴 하나로 읽힙니다.

--- 워치리스트 — 보유종목 변동 감지 ---

워치리스트의 핵심은 보유종목 변동 감지입니다.

사용자가 관심 ETF를 등록하면,
두 시점의 HOLDS를 비교해서 신규 편입, 편출, 비중 증가, 비중 감소로 분류합니다.
예를 들어 어떤 ETF가 SK하이닉스 비중을 15%에서 18.5%로 올렸다면
"비중 증가 +3.5%p"로 표시됩니다.

3%p를 넘는 변화가 있으면 알림을 보냅니다.
수집이 끝나면 PostgreSQL의 LISTEN/NOTIFY로 백엔드에 신호가 가고,
백엔드는 SSE로 앱에 알려서 상단에 알림 점이 뜹니다.
Discord 웹훅이 설정되어 있으면, 관리자의 WATCHES 관계를 따라 Discord로도 보냅니다.


========================================
ETF 테마 태깅
========================================

--- 태그 27개, 세 단계 ---

ETF에는 반도체, AI, 2차전지, 방산, 고배당 같은 테마 태그를 붙입니다. 모두 27개입니다.

태그는 세 단계로 붙입니다.

첫 번째는 지수 규칙입니다.
이름이 "200", "코스피", "KRX300"이나 "150", "코스닥" 같은 패턴이면
코스피 또는 코스닥 태그를 붙입니다.
이 두 태그는 규칙으로만 붙고 LLM은 쓰지 않습니다.

두 번째는 키워드 규칙입니다.
이름에 "반도체", "배터리", "원자력" 같은 단어가 있으면 해당 태그를 붙입니다.

세 번째가 LLM 분류입니다.
앞의 규칙에 걸리지 않은 ETF를 LLM에 보냅니다.
ETF 이름과 보유종목 상위 10개를 근거로 주고, structured output으로 태그를 고르게 합니다.
5개씩 묶어서 보내는데, 추론 모델이 생각하다가 토큰이 바닥나는 배치가 있어서
그런 배치는 thinking을 끄고 한 번 더 시도합니다.

하나 더, 시장 전체를 담는 ETF처럼 딱 맞는 테마가 없으면
태그를 붙이지 않아도 되도록 했습니다.
가장 가까운 태그를 억지로 고르게 했더니 오분류가 늘었기 때문입니다.

--- 신규 ETF만 태깅 ---

예전에는 매주 전체 ETF를 처음부터 다시 태깅했습니다.
그런데 LLM 결과가 실행마다 달라서, 같은 ETF의 태그가 주마다 바뀌었습니다.
어떤 주에는 "전력·원전"이었다가 다음 주에는 "전력·건설"이 되는 식입니다.

그래서 지금은 tagged_at이 없는 ETF, 즉 새로 편입된 ETF만 태깅합니다.
태그 규칙이나 태그 목록을 바꿨을 때만
full_rebuild 파라미터를 켜고 수동으로 실행해 전체를 다시 태깅합니다.

--- 관리자 수동 지정 ---

자동 태깅이 아무리 좋아져도 사람이 보기에 틀린 경우는 남습니다.

관리자 페이지에 "ETF 태그" 탭을 만들었습니다.
모든 ETF와 그 태그가 나오고,
셀렉트 박스로 태그를 추가하고 배지에서 바로 제거할 수 있습니다.
이렇게 손댄 ETF는 그 목록이 manual_tags로 고정되고,
태깅 DAG는 이 ETF에 규칙도 LLM도 적용하지 않고 지정된 태그를 그대로 씁니다.

우량주라는 태그는 수동으로만 붙습니다.
"산업 테마 없이 시가총액 상위, 성장성, ESG 같은 선별 기준으로 대형주를 골라 담는 ETF"를 뜻합니다.
지수를 폭넓게 따라가는 ETF는 계속 코스피 태그로 둡니다.
경계가 사람의 판단에 가까워서 LLM에 맡기지 않았습니다.


========================================
AI 챗봇
========================================

--- 전체 구조 ---

이제 챗봇입니다.

ChatService는 pydantic-ai tool-calling 에이전트 하나로 되어 있습니다.
LLM은 qwen38-27b, 임베딩은 embedding-gemma-300m(768차원)을 쓰고,
둘 다 LiteLLM 프록시(OpenAI 호환)를 거쳐 호출합니다.

도구는 10개입니다.
검색: etf_search, stock_search, list_tags
정보: get_etf_info, get_etf_prices, get_stock_prices, get_holdings_changes
분석: find_similar_etfs, compare_etfs, 그리고 Cypher를 직접 실행하는 graph_query

모든 도구가 내부적으로 Apache AGE 그래프를 조회합니다.
그래프와 에이전트가 여기서 만납니다.

--- 동작 흐름 ---

"삼성전자를 가장 많이 보유한 ETF는?"이라고 물으면 이렇게 흘러갑니다.

  [Step 1] stock_search(query="삼성전자")
  [Step 2] graph_query(cypher="MATCH (e:ETF)-[h:CURRENT_HOLDS]->(s:Stock {code: '005930'})
           RETURN {etf_code: e.code, etf_name: e.name, weight: h.weight}
           ORDER BY h.weight DESC LIMIT 5")
  [답변]   마크다운 표

모델이 도구 호출을 정하면 프로그램이 실행하고, 결과를 모델에 돌려줍니다.
모델이 도구 없이 답을 낼 때까지 반복합니다.
무한히 돌지 않도록 질문 하나당 모델 요청 수에 15회 상한을 뒀습니다.

run_stream_events로 받은 도구 호출과 결과는 단계 이벤트로 바꿔서
화면의 접이식 패널에 실시간으로 보여 줍니다.
사용자는 AI가 어떤 도구를 어떤 인자로 불러서 답을 만들었는지 투명하게 볼 수 있습니다.

--- Tool 정의 ---

도구는 이렇게 정의합니다.

  class ETFSearchTool(ChatTool):
      name = "etf_search"
      description = "ETF를 이름이나 코드로 검색합니다. ..."
      inputs = {
          "query": {"type": "string", "description": "검색 키워드"},
          "limit": {"type": "integer", "nullable": True,
                    "description": "최대 결과 수 (기본값 10)"},
      }

      def forward(self, query: str, limit: int = 10) -> str: ...

name, description, inputs, forward() 네 가지를 정의하면
as_agent_tool()이 pydantic-ai의 Tool.from_schema로 변환해 줍니다.
inputs는 JSON 스키마 형식이고, nullable이면 선택 인자입니다.

여기서도 핵심은 description입니다.
모델은 이 설명을 보고 도구를 고르고 인자를 채웁니다.
인자가 스키마에 맞지 않으면 재시도 프롬프트로 모델에 되돌아가고,
화면에는 오류 단계로 표시됩니다.

--- graph_query의 안전장치 ---

graph_query는 LLM이 쓴 Cypher를 그대로 실행하는 도구라 가장 위험합니다.
그래서 이렇게 막아 두었습니다.

- 별도 DB 연결에서 SET TRANSACTION READ ONLY, 읽기 전용 트랜잭션으로 실행하고 끝나면 롤백합니다
- statement_timeout을 10초로 겁니다
- 쿼리에 $$나 ;가 있으면 실행하지 않고 거부합니다. 앞에서 말씀드린 SQL 따옴표 탈출을 막는 겁니다
- 쿼리 오류가 나면 오류 메시지를 LLM에 그대로 돌려줘서 스스로 고치게 합니다

또 하나 재미있는 일이 있었습니다.
도구 결과는 사람이 읽기 좋게 비중에 %를, 순자산에 억원을 붙여서 돌려줍니다.
그런데 이걸 본 모델이 저장된 값도 문자열이라고 생각하고,
조건을 문자열 비교로 쓴 적이 있습니다.
그래서 graph_query 설명에 "값은 숫자로 저장돼 있고, 서식은 표시용이다"라고 분명히 적었습니다.

--- Few-shot — Cypher 패턴 예시 ---

챗봇의 정확도를 높이는 장치가 few-shot 예시입니다.

시드 예시 38개를 도구 호출 순서로 적어 뒀습니다.
예시의 핵심은 Cypher 구조이고,
고유명사는 <종목명1>, <ETF명>, <운용사> 같은 자리표시자로 둡니다.
종목은 Cypher 안에서 이름으로 바로 찾게 했습니다.
원본은 docker/db/seed/code_examples.py에 있고, 여기서 SQL을 생성합니다.

예를 들면 이런 예시입니다.

  Q: 삼성전자와 SK하이닉스가 많이 들어있는 ETF를 수수료순으로 정렬해줘
  graph_query(cypher="MATCH (e:ETF)-[h:CURRENT_HOLDS]->(s:Stock)
    WHERE s.name IN ['<종목명1>', '<종목명2>']
    WITH e, count(s) AS matched, sum(h.weight) AS weight_sum
    WHERE matched = 2
    RETURN {code: e.code, name: e.name, weight_sum: weight_sum, expense_ratio: e.expense_ratio}
    ORDER BY e.expense_ratio ASC, weight_sum DESC LIMIT 10")

예시를 찾는 방법도 바꿨습니다.
저장된 예시의 질문은 고유명사를 일반화해서 임베딩해 둡니다.
"삼성전자를…"이 "특정 종목을…"이 되는 식입니다.
사용자 질문이 들어오면 같은 방식으로 일반화한 뒤 pgvector로 가까운 예시 3개를 찾고,
일반화된 질문과 코드를 함께 프롬프트에 넣습니다.

일반화는 thinking을 끄고 돌립니다. 0.2~0.4초면 끝나고, 켰을 때와 결과가 같았습니다.

효과도 확인했습니다.
"현대차와 기아…"로 시작하는 질문은 예전에 엉뚱한 예시가 거리 0.29로 잡혔는데,
지금은 맞는 예시가 거리 0.19로 매칭됩니다.
"에코프로비엠과 포스코퓨처엠…"은 아예 매칭되는 예시가 없다가, 거리 0.16으로 잡히게 됐습니다.

관리자가 좋은 답변이 나온 채팅 로그를 승인하면,
그 로그도 같은 도구 호출 형식의 예시로 추가됩니다.
쓰면 쓸수록 예시가 늘어나는 피드백 루프입니다.

--- 설계 변천사 ---

지금 구조가 처음부터 이랬던 건 아닙니다. 다섯 단계를 거쳤습니다.

1단계는 ReAct만 쓰는 구조였습니다.
CodeAgent의 ReAct 패턴만 썼더니, 단순한 질문은 괜찮았지만
에이전트가 쓰는 Cypher의 정확도가 낮았습니다.
AGE의 Cypher는 Neo4j와 미묘하게 다른데, 모델이 그걸 알 리가 없으니까요.

2단계에서 Cypher few-shot을 넣었습니다.
Cypher 예시 100개를 준비하고 pgvector로 비슷한 예시를 찾아 넣었습니다.
단순 질의는 확실히 좋아졌습니다.
하지만 "반도체 ETF 3개의 수익률, 보유종목, 가격을 모두 비교해줘" 같은,
도구를 7~8번 불러야 하는 복잡한 질문에서는 방향을 잃었습니다.

3단계에서 분류기와 Plan-Execute-Summarize를 붙였습니다.
예상 도구 호출 수가 많은 질문이면 LLM이 계획을 JSON으로 세우고,
계획대로 도구를 실행한 뒤, 결과를 모아 요약하게 했습니다.
안정적이었지만 구조가 무거웠습니다.

4단계에서 한 가지 의문이 들었습니다.
"CodeAgent는 for 루프를 쓸 수 있는데, 외부 플래너가 왜 필요하지?"
그래서 PES를 걷어내고 ReAct 단일 경로로 돌아갔고,
예시도 CodeAgent에 맞춰 Python 코드로 바꿨습니다.

그리고 5단계, 지금의 구조입니다.
프레임워크를 pydantic-ai tool-calling으로 바꾸면서
예시는 다시 Cypher 패턴으로 돌아왔습니다.
대신 고유명사를 자리표시자로 일반화하고, 검색도 일반화된 질문끼리 비교합니다.

왜 진자가 다시 Cypher 쪽으로 돌아왔을까요.
돌이켜 보니 Python 예시가 실제로 도움을 준 건 Python 문법이 아니라
그 안에 들어 있던 Cypher 구조였습니다.
복잡한 조합은 Cypher 한 번이나 도구 몇 번으로 충분히 풀렸습니다.
그렇다면 읽기 전용 도구 호출로 같은 일을 할 수 있는데,
LLM이 만든 Python을 서버에서 실행하는 건 불필요한 위험이었습니다.
그리고 예전 Cypher 예시의 약점이었던,
고유명사가 박혀 있어서 엉뚱하게 매칭되던 문제는
자리표시자와 질문 일반화로 풀었습니다.


========================================
포트폴리오 관리 & 대시보드
========================================

--- 포트폴리오 관리 ---

마지막 주요 기능인 포트폴리오입니다.

사용자가 ETF와 주식의 매수 기록을 직접 입력하면, 현재가로 평가액을 계산합니다.
목표 비중을 정하면 실제 비중과의 차이와 리밸런싱 계산을 보여 줍니다.

보유 수량, 평균 단가, 스냅샷 금액 같은 민감한 값은
앱 단에서 AES-256-GCM으로 암호화해서 저장합니다.

--- 대시보드 ---

portfolio_snapshots 테이블에 포트폴리오별 일별 스냅샷이 쌓이고,
대시보드는 Recharts로 가치 변화를 그립니다.

스냅샷은 장중 10분마다 도는 실시간 가격 DAG가
가격을 수집한 직후에 갱신합니다.
포트폴리오마다 스냅샷 기록을 켜고 끌 수 있고,
같은 날짜의 스냅샷은 UNIQUE(portfolio_id, date) 제약으로 덮어씁니다.

과거 이력을 백필하지 않기 때문에, 추이 차트는 데이터가 쌓인 만큼만 보입니다.

이 기능은 관계형 테이블을 씁니다.
모든 걸 그래프에 넣지 않고,
CRUD와 트랜잭션 중심의 데이터는 관계형으로, 관계 탐색은 그래프로 나눈 설계입니다.


========================================
시행착오
========================================

--- "오늘"은 언제인가 — 기준일과 멱등성 ---

"장 마감 후에 그날 데이터를 저장한다."
단순해 보이지만, 기준일과 수집일을 구분하지 않고 출발했더니 여러 번 고쳐야 했습니다.

첫 번째, 데이터가 없는 것과 값이 0인 것은 다릅니다.
휴장일 다음 실행에서 새 가격 데이터가 없었는데,
수익률 계산이 이걸 "수익률 0%"로 처리해서 기존 값을 전부 0%로 덮어써 버렸습니다.
새 데이터가 없으면 기존 값을 건드리지 않도록 고쳤습니다.
없으면 그냥 아무것도 하지 않아야 합니다.

두 번째, 요청한 날짜와 데이터의 날짜는 다릅니다.
비거래일 날짜로 데이터를 요청하면 직전 거래일 데이터가 돌아오는데,
이걸 요청한 날짜로 저장했다가 가격 노드가 중복으로 생겼습니다.
지금은 영업일 목록 자체를 KIS 일봉이 돌려주는 실제 날짜로 만들고,
그 날짜를 XCom으로 하위 Task에 넘깁니다.
date.today()가 아니라 데이터가 알려주는 날짜를 쓰는 겁니다.

세 번째, 수동 재실행이 알림을 중복으로 보냈습니다.
DB 쓰기는 INSERT ... ON CONFLICT DO NOTHING으로 멱등적이었는데,
pg_notify와 Discord 알림은 INSERT 성공 여부와 관계없이 매번 나갔습니다.
INSERT 결과의 rowcount를 보고, 새 행이 생겼을 때만 알리도록 고쳤습니다.

네 번째, 스냅샷의 기준입니다.
한때 스냅샷 전용 DAG를 따로 뒀는데,
이게 가격 수집보다 먼저 돌면 어제 가격으로 오늘 스냅샷이 찍혔습니다.
결국 가격 수집 바로 뒤에 스냅샷을 갱신하도록 한 DAG로 합치고,
날짜별 UPSERT로 정리했습니다.

돌아보면 "기준일"과 "수집일"을 분리하고,
데이터가 알려주는 날짜를 쓰고,
데이터가 없으면 아무것도 하지 않는 것.
이 세 가지로 정리가 됐는데, 만들면서 하나씩 알게 된 것들입니다.

--- 장중의 미완성 일봉 ---

KIS로 옮긴 뒤에 새로 생긴 문제입니다.

오전 10시쯤 수집 DAG를 수동으로 돌린 적이 있습니다.
그런데 KIS 일봉 API는 장중에도 당일 봉을 돌려줍니다.
아직 장이 끝나지 않은, 미완성된 봉입니다.
그 결과 장중 가격이 그날 종가로 저장됐습니다.

더 나쁜 건, 다음 실행이 그 날짜를 이미 수집한 것으로 보고 넘어가기 때문에
잘못된 값이 저절로 고쳐지지 않는 구조였다는 겁니다.
그날은 그래프를 비우고 다시 수집해서 바로잡았습니다.

그래서 수집 범위의 끝을 "종가가 확정된 마지막 날"로 잘랐습니다.
16시 전에 실행되면 전날까지만 수집합니다.
이전 코드는 수집 범위를 항상 "오늘"까지 잡았기 때문에,
아침 8시 반 정기 실행도 같은 위험을 안고 있었습니다.
수동 실행 덕분에 정기 스케줄이 돌기 전에 드러난 셈입니다.

--- 이력이 쌓이는 관계 — HOLDS에서 CURRENT_HOLDS로 ---

앞에서 말씀드린 CURRENT_HOLDS도 시행착오의 결과입니다.

날짜별 이력 엣지는 하루에 약 4,100개씩 늘어납니다.
"최신 보유종목" 쿼리가 ETF마다 이력 전체를 훑고 있었는데,
지금은 데이터가 적어서 괜찮아도 1년 뒤면 약 100만 개를 훑게 됩니다.

현재 상태를 담는 CURRENT_HOLDS를 따로 두고, 이력은 비교에만 쓰도록 나눴습니다.
같은 관계라도 "현재"와 "이력"은 저장을 분리하는 편이 낫다는 교훈입니다.

--- LLM 태깅의 비결정성 ---

태깅 이야기에서 말씀드렸듯이, 같은 ETF가 주마다 다른 태그를 받았습니다.

LLM 출력은 실행마다 달라질 수 있다는 걸 전제로 설계를 바꿨습니다.
한 번 붙인 태그는 고정하고, 새로 들어온 ETF만 태깅합니다.
사람이 지정한 태그는 자동 태깅이 건드리지 않습니다.
전체 재태깅은 명시적으로 요청할 때만 합니다.
LLM을 매번 다시 돌리는 게 아니라, 결과를 한 번 확정하고 사람이 고칠 수 있게 한 겁니다.

--- 이름 기반 휴리스틱의 구멍 ---

이름으로 거르고 분류하는 규칙은 편리하지만 구멍이 생깁니다. 두 가지 사례가 있었습니다.

첫째, 은 ETF가 유니버스에 들어왔습니다.
원자재 ETF는 빼는 게 원칙인데, 은 관련 제외 키워드가 "은현물"뿐이라
"1Q 은액티브"가 그대로 통과했습니다.
그렇다고 "은"을 키워드로 넣으면 "은행" ETF까지 빠집니다.
단어 첫머리에 오는 "은", 그리고 뒤에 "행"이 오지 않는 경우만 잡는 정규식으로 고쳤습니다.

둘째, 운용사가 "기타"로 연결된 ETF가 7개 있었습니다.
IBK, FOCUS, DAISHIN 같은 브랜드가 매핑 표에 없었기 때문입니다.
이참에 마스터 파일에 남아 있던 미매핑 브랜드까지 함께 추가했습니다.

이름은 편리한 1차 필터지만, 규칙에 없는 이름은 조용히 새어 나갑니다.
"기타"나 미분류 개수처럼 새는 것을 드러내는 지표를 주기적으로 확인해야 한다는 걸 배웠습니다.

--- LLM이 쓴 쿼리의 보안 ---

가장 아찔했던 건 graph_query였습니다.

처음 graph_query는 postgres 슈퍼유저 권한으로 실행됐고,
CREATE, DELETE 같은 키워드 블랙리스트에만 기대고 있었습니다.
점검해 보니 TRUNCATE와 ALTER는 목록에 없었습니다.
게다가 쿼리에 $$를 넣으면 Cypher를 감싼 SQL 따옴표를 빠져나가서
임의의 SQL을 실행할 수 있었습니다.

지금은 읽기 전용 트랜잭션, 실행 시간 제한, $$와 ; 거부로 바꿨습니다.
금지어를 나열하는 대신 DB가 쓰기를 거부하게 만드는 쪽이 우회할 틈이 적습니다.
블랙리스트는 빠뜨린 걸 막지 못하지만, 읽기 전용 트랜잭션은 빠뜨릴 게 없으니까요.

--- 그래프 vs 관계형 — 어디에 뭘 넣을까 ---

마지막은 데이터를 어디에 둘지에 대한 이야기입니다.
처음에는 모든 데이터를 그래프에 넣으려고 했습니다.
해 보니 적합한 영역이 나뉩니다.

그래프에 적합한 것:
- 관계 탐색 (ETF-종목 보유, 유사 ETF, 태그)
- 시계열 + 관계 (날짜별 보유 비중 변화)
- 다대다 관계 (사용자-ETF 워치리스트)

관계형에 적합한 것:
- 단순 CRUD (사용자, 포트폴리오, 매수 기록)
- 집계·정렬 중심 조회 (스냅샷, 평가액)
- 트랜잭션이 중요한 데이터 (인증)

대표 사례가 가격 데이터입니다.
처음에는 etf_prices, stock_prices라는 관계형 테이블에 저장했습니다.
그런데 챗봇 도구가 모두 그래프를 조회하는 구조라서,
가격만 관계형에 있으니 SQL과 Cypher를 오가야 했습니다.
결국 Price 노드와 HAS_PRICE 관계로 옮기고 테이블은 없앴습니다.
저장소는 "주로 어디서 조회하느냐"에 맞춰야 한다는 교훈입니다.

"전부 그래프"나 "전부 관계형"이 아니라 데이터 특성에 맞게 섞어 쓰는 게 현실적입니다.
그리고 그 분리를 한 DB 안에서 할 수 있다는 게 Apache AGE의 장점입니다.


========================================
회고 & 마무리
========================================

--- 기술 선택 회고 ---

마지막으로 각 기술에 대한 평가입니다.
일반론이 아니라, 이 프로젝트에서 저희가 직접 겪은 것을 바탕으로 한 평가입니다.

Apache AGE:
- 좋았던 점: PostgreSQL 하나로 관계형, 그래프, 벡터 검색을 함께 운영할 수 있었습니다.
  Cypher도 결국 SQL 안에서 돌기 때문에
  읽기 전용 트랜잭션, statement_timeout, Alembic 같은 PostgreSQL 도구를 그대로 쓸 수 있었습니다.
- 아쉬운 점: Cypher 지원이 불완전합니다. WITH 별칭 정렬이나 MERGE+SET 같은 데서 막혔습니다.
  $$ 따옴표 안에 쿼리를 넣는 구조라 외부 입력을 다룰 때 신경 쓸 게 많고,
  이력이 쌓이는 관계는 모델링을 따로 고민해야 했습니다. 커뮤니티와 자료도 적습니다.
- 추천 상황: 이미 PostgreSQL을 쓰고 있고, 그래프 쿼리가 전체 워크로드의 일부일 때.

pydantic-ai (tool-calling):
- 좋았던 점: 가볍고 OpenAI 호환 엔드포인트에 바로 붙습니다.
  도구 인자를 스키마로 검증하고 틀리면 모델에 되돌려 줍니다.
  이벤트 스트림 덕분에 기존 SSE 형식을 유지한 채 프레임워크만 바꿀 수 있었고,
  무엇보다 LLM이 만든 코드를 실행하지 않아도 됩니다.
- 아쉬운 점: CodeAgent처럼 루프나 변수로 결과를 가공할 수 없어서,
  정렬과 필터는 모델이나 Cypher에 맡겨야 합니다.
  도구들이 DB 세션 하나를 공유해서 실행은 순차로 합니다.
  추론 모델을 쓰면 토큰 예산을 넉넉히 줘야 합니다.
- 추천 상황: 읽기 위주 도구 10개 안팎, 몇 단계면 끝나는 질의형 에이전트.
  계획, 파일시스템, 서브에이전트가 필요한 장기 작업이라면 더 무거운 프레임워크를 검토할 만합니다.
  참고로 처음 쓴 smolagents도 작고 읽기 쉬워서 프로토타이핑에는 좋았습니다.

Apache Airflow 3.x:
- 좋았던 점: 작업 흐름을 Python 코드로 관리하고 테스트할 수 있다는 것 자체가 큰 가치입니다.
  웹 UI, 재시도, 의존성 기반 병렬 실행, XCom, Params가 설정만으로 동작합니다.
- 아쉬운 점: 컨테이너가 api-server, scheduler, dag-processor, init으로 늘었고,
  2.x에서 올릴 때 import 경로와 이미지 구성을 손봐야 했습니다.
  "Hello World"까지 가는 단계가 많습니다.
  다만 한 번 세팅하면 이후에는 DAG 파일만 관리하면 됩니다.
- 추천 상황: Python 기반 배치 ETL과 정기 수집. 실시간 데이터 라우팅이 핵심이라면 NiFi 쪽이 맞습니다.

KIS Open API (데이터 소스):
- 좋았던 점: 키 하나로 ETF 목록, 현재가, 일봉, 구성종목, 휴장일까지 얻습니다.
  ETF 목록이 들어 있는 마스터 파일은 키도 필요 없습니다.
  주식 일봉을 종목당 기간 단위로 한 번에 받을 수 있어서 호출 수가 줄었습니다.
- 아쉬운 점: 구성종목은 상위 30개만 오고, 날짜 지정이 안 돼서 과거 백필이 불가능합니다.
  장중에는 미완성 일봉이 옵니다.
  토큰 발급과 초당 호출 제한을 직접 다뤄야 하고,
  순자산 단위처럼 문서에 없는 부분이 있으며, 총보수는 제공하지 않습니다.
- 추천 상황: 국내 시세를 일 단위로 꾸준히 쌓는 개인·리서치 프로젝트.
  정확한 전체 구성종목이나 과거 이력이 필요하다면 다른 소스를 함께 검토해야 합니다.
