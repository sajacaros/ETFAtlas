Chapter 01

오프닝

ETF Atlas는 한국 ETF 데이터를 매일 모아 그래프로 쌓고, 자연어로 물으면 표와 차트로 답하고(ETF가 담은 기업은 DART 공시·실적·정기보고서로 분석하고, 살지 말지 의견까지), 조건을 이어 종목을 골라 그 결과를 날마다 채점하는 웹 서비스입니다. 수집·리포트·매수 의견·챗봇 점검은 디스코드로 알려 옵니다. 기술 리서치 프로젝트로 시작해, 실제로 매일 돌아가는 서비스 수준까지 만들었습니다.

풀고 싶었던 문제

상장 ETF는 약 1,175개이고, 그중 국내 주식형·순자산 500억 원 이상만 골라도 193개, 이들이 담은 종목은 수천 건의 보유 관계를 이룹니다. "삼성전자를 가장 많이 담은 ETF는?", "KODEX 200과 비슷한 ETF는?" 같은 질문은 모두 관계 탐색입니다.

여기에 두 가지를 더 원했습니다. 개발자가 아니어도 자연어로 묻고 화면으로 답을 받는 것, 그리고 이 데이터가 매일 자동으로 쌓이는 것입니다.

관계 탐색은 Apache AGE, 자연어 질의는 pydantic-ai 기반 LLM 에이전트, 자동 수집은 Apache Airflow로 풀었습니다. 데이터 소스는 ETF·시세는 한국투자증권 KIS Open API, 기업 공시·실적·보고서는 금융감독원 DART OpenAPI입니다.
Chapter 02

기술 스택

Apache AGE — PostgreSQL 안의 그래프

PostgreSQL 확장으로 그래프와 Cypher 쿼리를 쓰게 해 줍니다. 별도 그래프 DB 서버 없이 관계형 테이블 + 그래프 + pgvector 임베딩을 한 DB에 둡니다. PostgreSQL 18 위에 AGE 1.8.0을 씁니다.

SELECT * FROM cypher('etf_graph', $$
    MATCH (e:ETF {code: '069500'})-[h:CURRENT_HOLDS]->(s:Stock)
    RETURN {stock: s.name, weight: h.weight}
    ORDER BY h.weight DESC LIMIT 10
$$) as (result agtype);

Cypher가 SQL 함수 안에서 돌기 때문에 읽기 전용 트랜잭션, 실행 시간 제한, Alembic 마이그레이션 같은 PostgreSQL 도구를 그대로 씁니다. 대신 Cypher 지원이 Neo4j보다 불완전하고 자료가 적습니다.

pydantic-ai — tool-calling 에이전트

LLM이 JSON 인자로 도구를 부르고, 인자는 스키마로 검증됩니다. 실행되는 코드는 우리가 작성한 도구뿐이라 LLM이 만든 코드를 실행할 일이 없습니다. 같은 프레임워크로 구조화된 출력(화면 설계, 태깅)도 받습니다. LLM과 임베딩은 LiteLLM 프록시(OpenAI 호환)를 거칩니다.

Apache Airflow 3.x — 배치 수집

"매일 아침 KIS에서 확정된 데이터를 받아 그래프에 적재한다"는 전형적인 배치 작업입니다. DAG를 Python 코드로 관리하고 테스트할 수 있고, 재시도·의존성 기반 병렬 실행·XCom을 설정만으로 씁니다. api-server, scheduler, dag-processor로 역할이 나뉜 3.x 구성입니다.

Chapter 03

전체 구성

기능

  • ETF 탐색 — 검색, 테마 태그·액티브/패시브 필터, 상세(보유종목, 유사 ETF, 가격)
  • 액티브 ETF 비중 변화 — 액티브 ETF가 종목 비중을 어떻게 바꿨는지 날짜별로, 전날·1주·1개월 전과 비교
  • 구성종목 분석 — ETF와 투자 비중을 넣으면 실제로 담기는 종목 비중을 계산
  • 포트폴리오 — 매수 기록, 목표 비중, 계좌 유형(IRP·연금저축), 일별 스냅샷 대시보드, 스냅샷 공유
  • AI 챗봇 — 자연어 질문에 표·차트·해설로 답하는 화면. ETF뿐 아니라 ETF가 담은 기업을 실적·밸류에이션·공시·정기보고서로 분석하고, 차트 신호와 "살까 말까"까지
  • 종목 스크리너 — 노드를 이어 종목을 고르고 AI로 근거를 정리, 고른 종목을 날마다 기록해 채점하고 자동 실행·알림
  • 디스코드 알림 — 비중 변화(아침), 일일 리포트(장 마감 뒤), 스크리너 종목 변동, 챗봇 점검(매일 아침), 주간 매수 의견(토요일)
  • 관리자 — 챗봇 로그 검수, 화면 설계 예시, ETF 태그, 알림 설정, DART 키

구성 요소

  • db — PostgreSQL 18 + Apache AGE + pgvector + pg_trgm
  • backend — FastAPI + pydantic-ai. 스크리너 자동 실행과 주간 매수 의견도 백엔드 프로세스 안에서 돕니다
  • frontend — React + TypeScript + Vite, nginx가 정적 파일을 서빙하고 /api를 백엔드로 넘김
  • airflow — 3.x, 수집·태깅·정기보고서 색인·챗봇 점검 DAG. 부팅 직후 DAG 폴더 마운트가 비어 있으면 컨테이너가 스스로 끝나 재시작됩니다

모두 Docker Compose로 띄웁니다. 외부에 열린 포트는 프런트엔드 하나이고, 백엔드·DB·Airflow는 내부에만 바인딩합니다. 가입은 초대 링크로 하고, 처음 만든 계정이 관리자가 됩니다.

하나의 PostgreSQL에서 CRUD는 관계형, 관계 탐색은 그래프, 예시 검색은 벡터로 나눕니다. 이 분리를 한 DB 안에서 할 수 있다는 것이 AGE를 고른 가장 큰 이유입니다.
Chapter 04

데이터 수집 — KIS Open API & Airflow

KIS에서 받는 것

  • ETF 목록 — 공개 종목 마스터 파일 (인증 불필요)
  • ETF 현재가 — NAV, 순자산, 상장주식수, 액티브/패시브 분류
  • 일봉 — ETF·주식 가격과 영업일 목록
  • ETF 구성종목 — 보유종목과 비중
  • 휴장일 — 개장 여부

총보수와 분배율(최근 12개월 분배금 ÷ 현재가)은 KIS가 주지 않아 네이버 증권에서, 포트폴리오의 장중 현재가와 스크리너가 쓰는 1년 일봉은 yfinance에서 받습니다.

DART에서 받는 것

챗봇의 기업 분석은 금융감독원 DART OpenAPI를 씁니다. 대상은 ETF들이 담은 종목(559개) 중 DART에 종목코드가 있는 회사입니다. 키는 관리자 페이지에서 등록하고 DB에 암호화해 둡니다.

  • 회사 고유번호 — 상장사 전체. 수집 ETF가 담지 않은 상장사를 물으면 "분석 대상이 아니다"라고 구분해 알립니다
  • 공시 목록 — 매일 최근 3일 치를 받아 담은 종목 것만 남깁니다
  • 주요계정 — 최근 5개 사업연도의 분기·반기·사업보고서 매출·영업이익·순이익·자산·부채·자본 (연결·별도 모두). 3년 연속 성장을 보려면 연간 실적 4개가 있어야 해서입니다
  • 현금흐름 — 영업활동현금흐름과 유·무형자산 취득(설비투자). FCF와 역산 DCF에 씁니다. 새 보고서·정정만 받고, 처음 채울 때는 하루 3,000건으로 나눠 키의 한도를 다른 작업과 나눠 씁니다
  • 정기보고서 원문 — 최근 1년 치를 받아 보관하고, 밤마다 목차 트리로 색인합니다 (Chapter 08)

유니버스 — 193개 ETF

레버리지·인버스·선물·합성·커버드콜, 채권·원자재·통화·리츠·해외 투자 ETF를 이름으로 거르고, 순자산 500억 원 이상만 남깁니다. 한 번 들어온 ETF는 빠지지 않고, 운용사는 이름 앞 브랜드(KODEX, TIGER…)로 연결합니다.

수집 원칙

  • 구성종목은 백필하지 않는다 — 구성종목 API에 날짜 지정이 없어 과거 보유종목은 얻을 수 없습니다. 첫 실행부터 하루씩 쌓습니다. 종가·거래량만은 일봉으로 지난 1년을 채울 수 있습니다
  • 가격은 확정된 날까지만 — 장중에는 미완성 일봉이 오므로 16시 전이면 전날까지만 받습니다
  • 구성종목은 개장일에, 공시된 날짜로 — KIS는 개장일 아침 08:30에 그날의 구성(직전 거래일 장 마감 기준)을 공시합니다. 개장일에만 받고 그날 날짜로 저장하며, 변화는 ETF별 직전 수집일과 비교합니다
  • 구성종목은 상위 30개 — API가 비중 상위 30개만 줍니다. 질의용 데이터라 그대로 쓰고, 전체 종목 수는 따로 표시합니다

DAG

  • chat_review (매일 08:00) — 전날 챗봇 대화 점검 → Discord (Chapter 07)
  • rdb_sync_metadata (매일 08:40) — 종목 마스터 → 관계형 ETF 목록
  • age_sync_universe (매일 08:50 · 16:30) — 영업일 → 유니버스·가격·프로필 → 구성종목 → 주식 가격 → 수익률 → 액티브 ETF 비중 변화 → 신규 ETF 태깅 → 수집 기록·Discord 알림. 아침에는 그날 공시된 구성종목을, 16:30에는 그날 종가를 받고 일일 리포트를 보냅니다
  • rdb_realtime_prices (평일 장중 10분마다) — 보유 티커 현재가 → 포트폴리오 스냅샷
  • dart_sync_rdb (평일 19:20) — DART 고유번호 → 공시 목록 · 주요계정 · 현금흐름
  • dart_report_index (매일 21:00, 밤새) — 정기보고서 원문 → 목차 트리 → 노드 요약 → 개요
  • age_tagging (토 03:00) — 테마 태깅
  • backfill_prices · embed_code_examples (수동) — 가격 이력 백필, 챗봇 예시 임베딩

모든 쓰기는 같은 날짜로 다시 돌려도 결과가 같게 만들었고, 조회에 실패한 ETF는 이전 값을 유지합니다.

Chapter 05

그래프 모델과 활용

etf_graph

  • CURRENT_HOLDS {date, weight} — ETF별 현재 보유종목(최대 30개). 수집할 때마다 교체하고, 현재 구성 조회는 모두 이것을 씁니다
  • HOLDS {date, weight} — 날짜별 보유 이력. 비중 변화를 비교할 때만 씁니다
  • HAS_PRICE — ETF와 종목 모두 날짜별 Price 노드로 가격을 가집니다

이력은 하루 약 4,100개씩 늘어납니다. "현재 보유종목"을 이력에서 매번 찾으면 데이터가 쌓일수록 느려지므로, 현재와 이력을 다른 관계로 나눴습니다. 현재 조회는 ETF당 30개 이하의 엣지만 읽습니다.

유사 ETF

공통 보유종목마다 두 비중 중 작은 값을 더하고, 기준 ETF의 비중 합으로 나눠 정규화합니다. 상위 30개만 있어 비중 합이 100%가 아니기 때문입니다.

MATCH (e1:ETF {code: $code})-[h1:CURRENT_HOLDS]->(s:Stock)
      <-[h2:CURRENT_HOLDS]-(e2:ETF)
WHERE e1 <> e2
WITH e2, COUNT(s) AS overlap,
     SUM(CASE WHEN h1.weight < h2.weight
         THEN h1.weight ELSE h2.weight END) AS similarity
RETURN {code: e2.code, name: e2.name, similarity: similarity}
ORDER BY similarity DESC LIMIT 5

관계형이면 자기 조인과 집계가 얽힐 쿼리가 MATCH 패턴 하나로 읽힙니다.

액티브 ETF 비중 변화

수집이 끝나면 Airflow가 모든 액티브 ETF를 직전 수집일과 비교해 신규 편입·편출·비중 증감을 계산하고 한 테이블에 저장합니다. 웹의 비중 변화 화면, 메뉴 배지, Discord 알림이 모두 이 결과를 읽으므로 서로 다른 숫자가 나오지 않습니다. 알림 기준(%p)은 관리자 페이지에서 정하고 읽을 때 적용합니다.

화면에서는 비교 기간을 고릅니다. 전날 비교는 위의 결과를 그대로 읽고, 1주·1개월은 HOLDS 이력에서 7일·30일 전 또는 그 이전의 마지막 수집일과 비교합니다.

Chapter 06

ETF 테마 태깅

반도체, AI, 2차전지, 방산, 고배당 같은 태그 27개를 씁니다. 순서대로 붙입니다.

  • 지수 규칙 — "200", "코스피", "코스닥" 같은 이름 패턴으로 코스피/코스닥
  • 키워드 규칙 — 이름에 "반도체", "배터리", "원자력" 등이 있으면 그 태그
  • LLM 분류 — 나머지는 이름과 상위 보유종목을 근거로 LLM이 구조화된 출력으로 고릅니다. 맞는 테마가 없으면 붙이지 않습니다

LLM 결과는 실행마다 달라질 수 있어, 한 번 붙인 태그는 고정하고 새로 들어온 ETF만 태깅합니다. 전체 재태깅은 명시적으로 요청할 때만 합니다.

관리자가 직접 지정한 태그는 자동 태깅이 건드리지 않습니다. 사람의 판단에 가까운 "우량주"는 수동으로만 붙습니다.

Chapter 07

AI 챗봇 — 답을 화면으로

챗봇은 글로만 답하지 않습니다. 질문을 보고 화면을 먼저 설계하고, 화면의 각 영역을 스킬이 채웁니다. 스킬은 21개이고, ETF(가격·수익률·비교·구성종목·겹침·순위), 기업(실적·밸류에이션·유형·공시·정기보고서), 차트 분석, 매수 의견, 해설을 맡습니다. 자세한 흐름은 Architecture 페이지에 있습니다.

처리 순서

  • 질문 재작성 — 이전 대화가 있으면 "이거 구성종목은?"을 독립된 질문으로. 잘못 읽었으면 원문 그대로 다시 물을 수 있습니다
  • 화면 설계 — Planner(LLM)가 화면을 줄과 슬롯으로 나누고, 슬롯마다 스킬·표시 방식·인자를 정합니다. 비슷한 질문의 설계 예시를 임베딩으로 찾고 LLM이 같은 유형만 골라 참고합니다. 출력 스키마는 등록된 스킬에서 만들어 모델이 생성하는 단계에서 강제하므로 형식이 틀릴 일이 없고, 재시도는 없는 이름·참조 오류 같은 내용 검사에만 씁니다
  • 슬롯 채우기 — 데이터 스킬이 그래프와 DART 테이블을 조회해 표·차트 데이터를 만듭니다. 서로 독립된 슬롯은 동시에 돌고, 끝나는 대로 화면에 나타납니다. "SK하이닉스를 담은 ETF 중 1주 수익률 상위 3개"처럼 한 슬롯의 결과를 다른 슬롯이 번호로 받아 쓰고, 받는 쪽이 ETF를 원하는데 종목을 넘기는 식의 어긋남은 설계 단계에서 막습니다
  • 한 번 다시 설계 — "ETF가 아니라 종목이었다"처럼 고칠 수 있는 이유로 빈 영역이 생기면, 실행 결과를 보여 주고 그 슬롯만 다시 설계합니다. 이미 그려진 영역은 흔들리지 않습니다
  • 해설 — 마지막 슬롯이 앞 영역의 요약만 보고 해설을 흘려보냅니다

숫자는 LLM을 거치지 않는다

표와 차트의 숫자는 DB에서 곧바로 옵니다. LLM은 화면 설계와 해설, 정기보고서 읽기만 하고, 해설에는 단위를 붙인 짧은 요약만 넘어갑니다. 그래서 숫자를 지어낼 틈이 없고, 일반 질문은 7~10초 안에 답합니다. 기간 수익률, 실적, 밸류에이션, 차트 신호 같은 계산은 app/domain에 모아 챗봇과 스크리너가 같은 함수를 씁니다. 예외는 정기보고서처럼 원문이 글과 표뿐인 경우이고, 이때는 LLM이 옮긴 숫자를 원문과 대조합니다(Chapter 08).

스킬로 안 되는 질문 — agent

스킬로 표현할 수 없는 질문은 agent 슬롯 하나로 넘깁니다. 안에서는 tool-calling 에이전트가 돌고, 도구는 둘로 나뉩니다. 검색·ETF 정보·유사 ETF·비교·가격 같은 도구 10개, 그리고 데이터 스킬 9개(실적·밸류에이션·유형·공시·차트 분석·기간 수익률·순위·겹침·포트폴리오)입니다. 스킬을 도구로 부르면 슬롯과 같은 요약을 돌려받아, 같은 계산이 두 벌로 갈라지지 않습니다. 도구 중 graph_query는 LLM이 쓴 Cypher를 직접 실행합니다.

  • 읽기 전용 트랜잭션, 실행 시간 10초 제한, SQL 따옴표를 탈출할 수 있는 $$·; 거부
  • pgvector로 비슷한 질문의 Cypher 패턴 예시를 찾아 프롬프트에 넣습니다. 고유명사는 자리표시자로 일반화해 엉뚱한 예시가 걸리지 않게 합니다
  • 어떤 도구를 어떤 인자로 불렀는지 화면에 단계별로 보여 줍니다

매일 아침 스스로 점검한다

매일 08:00 chat_review DAG가 전날 대화를 읽습니다. 먼저 LLM 없이 신호를 모읍니다: 실패·중지·되묻기로 끝난 답, 비거나 실패한 영역, 싫어요, 반복된 도구 오류, 같은 질문인데 영역 구성이 달랐던 경우. 그다음 LLM이 세션 전체를 보고 문제 턴과 원인(스킬 선택, 영역 구성, 스킬 결과, 도구, 없는 기능, 데이터 없음, 중단)과 고칠 곳을 골라 Discord로 보냅니다. 다음 턴의 사용자 말("재무 스킬에서 가져오면 되잖아")이 가장 강한 신호라 턴 하나만 보지 않습니다.

이 봇은 보고만 합니다. 스킬 설명, 레이아웃 예시, 코드는 사람이 고치고, 고친 뒤에는 평가 세트로 다른 질문이 무너지지 않았는지 확인합니다.

대상이 애매하면("반도체 ETF 구성종목") 하나를 추측하지 않고 후보를 보여 주며 되묻습니다. 멈추면 화면은 바로 끝나고, 답변마다 완료·중지·실패·되묻기 중 어떻게 끝났는지 남습니다. 관리자가 검수한 대화와 설계 예시, 점검 봇이 찾은 약점이 다시 챗봇을 고치는 재료가 됩니다.
Chapter 08

기업 분석 — DART와 정기보고서

"삼성전자 분석해줘"에는 주가 추이와 담은 ETF(이 서비스만의 데이터) 옆에 DART 분기 실적, 최근 공시, 가장 최근 정기보고서를 놓고 해설로 묶습니다. 모두 Airflow가 미리 받아 둔 테이블에서 읽습니다. 수집 ETF가 담지 않은 상장사는 "분석하지 않는 종목"이라고 한 번만 알립니다.

실적 · 밸류에이션 · 유형

  • 실적 — 분기·연간 매출·영업이익·순이익과 영업이익률, 부채비율. 4분기는 연간에서 3분기 누적을 빼 구하고, 빠진 분기는 0으로 채우지 않고 비웁니다
  • 밸류에이션 — 시가총액은 종가 × 상장주식수, 여기에 DART 실적을 붙여 PER(최근 4분기·직전 연도)·PBR·ROE를 직접 계산합니다. 영업현금흐름 − 설비투자로 FCF와 FCF 수익률을, 지금 시가총액을 정당화하려면 FCF가 몇 % 성장해야 하는지 역산 DCF로 냅니다. KIS의 PER·PBR은 대조용으로 함께 보여 줍니다
  • 유형 판정 — 지속 성장주, 턴어라운드주, 경기민감·성숙기, 신흥·초기 단계를 연속 성장, 영업이익률, 발생액 품질, 흑자 반등, 영업현금흐름 같은 숫자 기준으로 가립니다. 해자처럼 숫자로 못 보는 기준은 "보고서로 확인할 것"으로 남깁니다

정기보고서 — 목차를 보고 골라 읽는다

정기보고서는 한 건이 70만 자에 이릅니다. 앞부분 몇 장만 잘라 요약하면 연구개발비, 직원 수, 최대주주, 배당, 감사의견처럼 요약 틀 밖의 질문에 답할 수 없습니다. 그래서 사람이 보고서를 읽는 방식을 따랐습니다. 목차를 보고, 답이 있을 절을 고르고, 그 절만 읽습니다(PageIndex 방식, 직접 구현).

  • 밤에 색인 — dart_report_index가 최근 1년 정기보고서 원문을 받아 보관하고, 장·절·주석을 노드로 하는 트리를 만듭니다. DART 원문은 목차가 태그로 정해져 있어 규칙으로 정확히 나눕니다. 표는 병합 셀을 풀어 한 행만 떼어 읽어도 뜻이 통하게 저장합니다
  • 노드 요약은 고르기용 — 노드마다 "이 절에 든 항목"을 LLM이 한 줄로 적어 둡니다. 답이 아니라 목차를 읽기 쉽게 하는 표지입니다. 신용등급이 '회사의 개요'에, 연구개발비 비율이 '주요계약 및 연구개발활동'에 있는 것처럼 제목만으로는 짐작하기 어려운 절을 찾게 해 줍니다
  • 질문이 오면 — LLM이 목차(제목 + 요약)를 보고 절 1~3개를 고르고, 그 절만 읽어 답합니다. 답 머리에 읽은 절과 DART 원문 링크를 붙여 출처를 확인할 수 있게 합니다. 수치는 원문 단위 그대로 옮깁니다
  • 개요 — 무엇을 찾는지 없이 물으면 사업 구조·영업 상황·위험 요인·소송·제재로 정리한 개요를 보여 줍니다. 밤에 미리 만들어 둡니다

삼성전자 보고서 2건에 질문 24개씩을 물었을 때, 목차에 제목만 넣으면 보고서마다 19개, 노드 요약까지 넣으면 24개 모두 정답 절을 골랐습니다. 답의 수치도 원문과 같았고, 질문당 3~9초가 걸립니다.

매출 구성 차트

보고서 표에서 부문·제품·지역·주요 고객별 매출을 LLM이 옮기되, 값과 항목 이름이 원문에 그대로 있을 때만 씁니다. 합계와 맞으면 도넛, 내부거래가 섞여 합이 전체가 아니면 막대로 그립니다. 계획에는 "보고서" 슬롯 하나만 있고, 스킬이 실행하며 매출 구성이 있으면 그 자리를 차트와 요약으로 나눕니다. 무엇이 나올지는 원문을 봐야 알기 때문입니다.

정기보고서는 원문 · 구조(목차 트리) · 색인(노드 요약)의 세 층으로 저장합니다. 파서를 고치면 DART를 다시 부르지 않고 보관한 원문으로 트리를 다시 만들고, 내용이 바뀐 노드만 다시 요약합니다.
Chapter 09

차트 분석과 매수 의견

차트 분석 — 대가들의 규칙을 코드로

"주가 분석해줘", "RSI 어때?"에는 봉차트에 이동평균·볼린저 밴드, 거래량, 넘겨 보는 보조지표 칸(MACD·RSI·스토캐스틱)을 그리고, 그 아래에 지표별 강세·약세 신호를 한 줄로 붙입니다. 신호는 LLM이 아니라 이름난 규칙을 옮긴 코드가 정합니다.

  • 추세 — 스탠 와인스타인의 단계 분석(150일선의 기울기와 그 위·아래)과 마크 미너비니의 트렌드 템플릿 충족 수
  • MACD — 알렉산더 엘더의 삼중 스크린. 교차가 아니라 히스토그램의 기울기를 봅니다
  • RSI — 앤드루 카드웰의 레인지 시프트. 30·70 고정이 아니라 최근 60거래일이 머무는 범위로 강세·약세를 가립니다
  • 스토캐스틱 — 혼자 판정하지 않고, 추세 안에서 "상승 추세 속 눌림"처럼 읽습니다

해설은 지표마다 지금 상태만 씁니다. 지지선·저항선, 앞으로의 방향, 매수·매도 판단은 쓰지 않습니다. 대가들의 규칙도 경험칙이라, 맞는지는 스크리너에서 앞으로 쌓아 채점해 확인합니다.

살까 말까 — LLM은 판정하고 규칙이 종합한다

"삼성전자 지금 사도 될까?"에는 차트 분석, 분기 실적·밸류에이션·유형 판정, 정기보고서 개요를 놓고, 마지막 영역에서 세 관점(차트·재무·보고서)마다 긍정~부정 판정과 근거를 냅니다. LLM은 앞 영역의 요약에 있는 사실·수치로만 판정합니다.

종합 의견(사 볼 만하다 · 지켜본다 · 사지 않는 편이 낫다)은 LLM이 아니라 규칙이 정합니다. 관점 평균이 +1 이상이고 부정인 관점이 없으면 사 볼 만하다, −1 이하면 사지 않는 편이 낫다, 그 사이나 부정이 하나라도 있으면 지켜봅니다. 네 유형 어디에도 맞지 않는 종목은 관점과 상관없이 사지 않습니다. 같은 판정이면 늘 같은 종합이 나오고, 왜 그 종합인지 규칙으로 설명할 수 있습니다.

주간 매수 의견

토요일 아침에는 ETF가 담은 주식 전체(약 570종목)에 같은 판정을 돌립니다. '사 볼 만하다' 중 점수가 높은 10개를 회사 한 줄 소개, 관점별 판정, 유형과 함께 Discord로 보내고, 지난주에 없던 종목에는 🆕를 붙입니다. 판정한 종목은 바로 저장해 백엔드가 중간에 다시 떠도 이어서 돌고, 한 주에 한 번만 보냅니다.

매수 의견은 이 서비스가 모은 데이터(시세·DART 실적·정기보고서)를 정해진 관점으로 읽은 참고 의견이지 투자 권유가 아닙니다. 화면과 알림 모두에 그렇게 밝힙니다.
Chapter 10

종목 스크리너 — 고르고, 쌓고, 채점한다

챗봇이 "묻는 것"이라면 스크리너는 "고르는 것"입니다. 캔버스에 노드를 놓고 이어 대상 종목 → 필터 → AI 분석 → 결과 순서를 만들고, 갈래를 나눠 따로 거른 뒤 교집합·합집합으로 합칠 수 있습니다. 자주 쓰는 조합은 추천 조합으로 바로 불러옵니다.

노드

  • 대상 종목 — ETF가 담은 전체 종목(559개), 특정 ETF의 구성종목, 내 포트폴리오가 ETF로 실제 담은 종목, 직접 입력
  • 차트 필터 — 이평 정배열, 고가 대비 위치, 20일 수익률, 거래량 배수, RSI, 간이 VCP, 그리고 "언제 시작됐나"를 묻는 조건: 최근 N거래일 안의 MACD·스토캐스틱 골든크로스(과매도에서 난 교차만 고를 수 있다), 볼린저 %B 범위. 지표는 챗봇 차트 분석과 같은 함수입니다
  • ETF 신호 필터 — 담은 ETF 수, 최근 공시일에 액티브 ETF가 새로 편입하거나 비중을 늘린 수. 이 서비스가 매일 쌓는 데이터라 다른 스크리너에는 없는 조건입니다
  • AI 분석 — 계산된 지표만 받아 종목마다 3문장으로 근거를 정리합니다. 매수·매도 권유와 예측은 쓰지 않습니다

과거로 돌리지 않고 앞으로 쌓는다

조건이 쓸모 있는지 보려면 백테스트를 떠올리지만, 구성종목 이력이 없어 "오늘 ETF가 담은 종목"으로 과거를 돌리게 됩니다. 이미 오른 종목만 고르는 생존 편향입니다. 그래서 저장한 스크리너는 돌릴 때마다 결과에 닿은 종목을 그날 날짜로 남기고, 나중에 채점합니다.

  • 기록한 날 다음 거래일 종가에 같은 금액으로 샀다고 봅니다. 장중에 돌렸거나 그날 종가를 보고 골랐어도 미래 값을 쓰지 않습니다
  • 5·20·60거래일 뒤 수익률을 KODEX 200과 비교해 초과수익과 적중률(지수보다 많이 오른 종목 비율)을 냅니다. 이긴 종목과 진 종목의 평균 초과수익을 따로 내 손익비를 보므로, 드물게 이기지만 크게 이기는 스크리너도 드러납니다. 거래 비용은 빼지 않습니다
  • 화면에서 고친 뒤 저장하지 않은 그래프의 결과는 남기지 않습니다. 무엇을 채점하는지 흐려지기 때문입니다

자동 실행과 알림

자동 실행을 켜면 영업일 장 마감 뒤 KODEX 200의 그날 일봉이 들어오는 대로 저장된 스크리너를 한 번 돌려 기록합니다. 휴장일은 일봉이 없어 저절로 건너뜁니다. 알림을 켜면 전날과 비교해 새로 들어오거나 빠진 종목만 Discord로 보냅니다.

숫자는 서버가 계산하고 LLM은 문장만 쓴다는 챗봇의 원칙을 그대로 따릅니다. 시세는 기능을 검증하는 단계라 yfinance에서 받고, 어떤 기간·지표가 필요한지 정해지면 KIS 일봉 수집으로 바꿀 수 있게 시세 공급원을 인터페이스 하나로 감쌌습니다.
Chapter 11

포트폴리오 관리 & 대시보드

사용자가 ETF와 주식의 매수 기록을 입력하면 현재가로 평가액을 계산하고, 목표 비중과의 차이로 리밸런싱을 보여 줍니다. 보유 수량·평균 단가·스냅샷 금액은 앱에서 AES-256-GCM으로 암호화해 저장합니다.

포트폴리오마다 계좌 유형(IRP·연금저축)을 하나 이상 붙입니다. 계좌마다 담을 수 있는 상품이 달라서입니다.

스냅샷을 켠 포트폴리오는 장중 10분마다 가격을 받은 직후 일별 스냅샷을 갱신하고, 대시보드는 그 추이를 그립니다. 스냅샷을 끄면 그동안의 기록을 지워, 다시 켰을 때 빈 기간이 섞이지 않게 합니다.

공유는 그 순간의 이름·계좌 유형·목표 비중을 스냅샷으로 저장합니다. 원본을 고쳐도 공유한 내용은 그대로이고, 공유 목록은 공유한 사람·계좌 유형으로 걸러 볼 수 있습니다.

포트폴리오는 관계형 테이블을 씁니다. CRUD와 트랜잭션 중심 데이터는 관계형, 관계 탐색은 그래프라는 분리를 그대로 따릅니다.
Chapter 12

만들며 정한 원칙

날짜를 정확히

"데이터가 없음"과 "값이 0"은 다르고, "요청한 날짜"와 "데이터의 날짜"도 다릅니다. 새 데이터가 없으면 기존 값을 건드리지 않고, 저장 날짜는 API가 돌려준 실제 날짜와 공시일을 씁니다. 모든 쓰기는 다시 돌려도 결과가 같아야 합니다.

현재와 이력은 따로

같은 관계라도 "지금"을 묻는 조회와 "변화"를 묻는 조회는 저장을 나눕니다(CURRENT_HOLDS / HOLDS).

저장소는 조회하는 곳에 맞춘다

그래프

  • ETF-종목 보유, 유사 ETF, 태그
  • 날짜별 보유 비중과 가격
  • 챗봇이 조회하는 모든 것

관계형

  • 사용자, 포트폴리오, 매수 기록
  • 스냅샷, 챗봇 로그, 비중 변화, 스크리너 기록
  • DART 공시·실적·현금흐름, 정기보고서 원문·목차 트리·노드 요약
  • 매수 의견 기록
  • 트랜잭션이 중요한 데이터

LLM은 결정적이지 않다

숫자는 LLM 밖에서 만들고, 한 번 정한 결과(태그, 보고서 개요·노드 요약)는 고정하며, 사람이 정한 값이 자동 결과보다 우선합니다. LLM이 쓴 쿼리는 금지어 목록 대신 DB가 쓰기를 거부하게 막습니다. LLM이 원문에서 옮긴 숫자는 믿지 않고 원문에 그대로 있는지 대조해, 하나라도 없으면 그 표를 버립니다.

LLM은 고르고 읽고, 규칙이 정한다

LLM에게는 잘하는 일만 맡깁니다. 화면에 무엇을 놓을지 고르고, 목차에서 답이 있는 절을 고르고, 요약을 읽어 관점마다 판정하는 일입니다. 차트 신호와 매수 의견의 종합처럼 "같은 입력이면 같은 답"이어야 하는 결정은 규칙이 합니다. 출력 형식도 모델이 생성하는 단계에서 스키마로 강제해, 형식을 고치느라 재시도하지 않습니다.

긴 문서는 미리 색인한다

질문이 올 때마다 긴 원문을 잘라 읽으면 잘린 곳의 답은 영영 나오지 않고, 처음 묻는 사람은 수십 초를 기다립니다. 보고서는 밤에 목차 트리와 고르기용 요약으로 색인해 두고, 질문이 오면 필요한 절만 읽습니다. 매수 의견이 읽는 개요도 미리 만들어 둡니다.

자동은 보고하고, 사람이 고친다

챗봇 점검 봇은 약점을 찾아 알리기만 하고 스킬·예시·코드를 건드리지 않습니다. 고친 것은 평가 세트로 다른 질문이 무너지지 않았는지 본 뒤 반영합니다.

검증은 앞으로 쌓아서

과거 데이터가 없는 것을 과거 데이터로 메우지 않습니다. 구성종목처럼 그날만 얻을 수 있는 데이터는 그날부터 쌓고, 스크리너의 쓸모도 백테스트 대신 기록한 날 이후의 실제 수익으로 따집니다.

새는 것을 드러낸다

이름 기반 필터는 편리하지만 규칙에 없는 이름은 조용히 새어 나갑니다. 운용사 "기타", 미분류 태그처럼 새는 것을 보여 주는 지표를 주기적으로 확인합니다.

Chapter 13

회고 & 마무리

Apache AGE

Good

PostgreSQL 하나로 관계형 + 그래프 + 벡터를 운영하고, PostgreSQL 도구를 그대로 씁니다.

Bad

Cypher 지원이 불완전하고 자료가 적습니다. 쿼리를 SQL 따옴표 안에 넣는 구조라 외부 입력에 신경 쓸 게 많습니다.

Recommend

이미 PostgreSQL을 쓰고 있고 그래프 쿼리가 워크로드의 일부일 때.

pydantic-ai

Good

가볍고 OpenAI 호환 엔드포인트에 바로 붙습니다. 도구 인자와 구조화된 출력을 스키마로 검증하고, 틀리면 모델에 되돌려 고치게 합니다.

Bad

도구 호출만으로는 결과를 자유롭게 가공하기 어려워, 정렬·필터는 Cypher나 스킬 쪽에 맡겨야 합니다.

Recommend

읽기 위주 도구 10개 안팎의 질의형 에이전트, 그리고 LLM에게 구조를 받는 일.

Apache Airflow 3.x

Good

수집 흐름을 Python 코드로 관리하고 테스트합니다. 재시도, 병렬 실행, 웹 UI가 설정만으로 동작합니다.

Bad

컨테이너가 여럿으로 나뉘어 처음 띄우기까지 단계가 많습니다.

Recommend

Python 기반 배치 ETL과 정기 수집.

KIS Open API

Good

키 하나로 ETF 목록, 현재가, 일봉, 구성종목, 휴장일까지 얻습니다.

Bad

구성종목은 상위 30개뿐이고 과거 이력이 없습니다. 총보수는 제공하지 않습니다.

Recommend

국내 시세를 일 단위로 꾸준히 쌓는 개인·리서치 프로젝트.

DART OpenAPI

Good

키 하나로 상장사 공시 목록, 여러 회사의 주요계정·현금흐름, 정기보고서 원문까지 받습니다. 원문 XML은 장·절이 태그로 정해져 있어 목차 트리를 규칙으로 정확히 만들 수 있습니다.

Bad

표 모양은 회사마다 달라 병합 셀과 여러 줄 머리말을 풀어야 하고, 매출 구성 같은 숫자는 표에서 옮긴 뒤 원문과 대조해야 합니다. 현금흐름은 회사·보고서마다 한 번씩 불러야 해 처음 채울 때 하루 2만 건 한도를 나눠 씁니다. 정정 공시 중에는 원문을 주지 않는 것도 있습니다.

Recommend

국내 상장사의 실적·공시를 정형 데이터로 쌓고, 보고서 원문은 보관해 색인하는 용도.

목차 트리 색인 (PageIndex 방식)

Good

임베딩 검색 없이 목차와 고르기용 요약만으로 질문 24개 모두 정답 절을 골랐습니다. 읽은 절을 밝혀 출처가 분명하고, 요약 틀 밖의 질문에도 답합니다.

Bad

노드 요약에 LLM 호출이 많아, 처음 색인은 보고서 수천 건을 2~3일 밤에 나눠 끝냅니다. 같은 LLM을 챗봇과 나눠 써서 동시 수를 높이지 못합니다.

Recommend

목차 구조가 분명한 긴 문서(공시, 규정, 매뉴얼)에서 사실을 찾아 답할 때.

yfinance

Good

키 없이 수백 종목의 1년 일봉을 한 번에 받아, 스크리너의 지표를 먼저 써 보고 무엇을 수집할지 정할 수 있습니다.

Bad

비공식 API라 막히거나 형식이 바뀔 수 있고, 코스피·코스닥 구분을 종목마다 찾아야 합니다.

Recommend

기능 검증 단계의 시세. 운영 데이터는 확정 시세를 쌓는 쪽으로.
