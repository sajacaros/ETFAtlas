Chapter 01

오프닝

ETF Atlas는 한국 ETF 데이터를 매일 모아 그래프로 쌓고, 자연어로 물으면 표와 차트로 답하는 웹 서비스입니다. 기술 리서치 프로젝트로 시작해, 실제로 매일 돌아가는 서비스 수준까지 만들었습니다.

풀고 싶었던 문제

상장 ETF는 약 1,175개이고, 그중 국내 주식형·순자산 500억 원 이상만 골라도 190개, 이들이 담은 종목은 수천 건의 보유 관계를 이룹니다. "삼성전자를 가장 많이 담은 ETF는?", "KODEX 200과 비슷한 ETF는?" 같은 질문은 모두 관계 탐색입니다.

여기에 두 가지를 더 원했습니다. 개발자가 아니어도 자연어로 묻고 화면으로 답을 받는 것, 그리고 이 데이터가 매일 자동으로 쌓이는 것입니다.

관계 탐색은 Apache AGE, 자연어 질의는 pydantic-ai 기반 LLM 에이전트, 자동 수집은 Apache Airflow로 풀었습니다. 데이터 소스는 한국투자증권 KIS Open API입니다.
Chapter 02

기술 스택

Apache AGE — PostgreSQL 안의 그래프

PostgreSQL 확장으로 그래프와 Cypher 쿼리를 쓰게 해 줍니다. 별도 그래프 DB 서버 없이 관계형 테이블 + 그래프 + pgvector 임베딩을 한 DB에 둡니다. PostgreSQL 18 위에 AGE 1.8.0을 씁니다.

SELECT * FROM cypher('etf_graph', $$
    MATCH (e:ETF {code: '069500'})-[h:CURRENT_HOLDS]->(s:Stock)
    RETURN {stock: s.name, weight: h.weight}
    ORDER BY h.weight DESC LIMIT 10
$$) as (result agtype);

Cypher가 SQL 함수 안에서 돌기 때문에 읽기 전용 트랜잭션, 실행 시간 제한, Alembic 마이그레이션 같은 PostgreSQL 도구를 그대로 씁니다. 대신 Cypher 지원이 Neo4j보다 불완전하고 자료가 적습니다.

pydantic-ai — tool-calling 에이전트

LLM이 JSON 인자로 도구를 부르고, 인자는 스키마로 검증됩니다. 실행되는 코드는 우리가 작성한 도구뿐이라 LLM이 만든 코드를 실행할 일이 없습니다. 같은 프레임워크로 구조화된 출력(화면 설계, 태깅)도 받습니다. LLM과 임베딩은 LiteLLM 프록시(OpenAI 호환)를 거칩니다.

Apache Airflow 3.x — 배치 수집

"매일 아침 KIS에서 확정된 데이터를 받아 그래프에 적재한다"는 전형적인 배치 작업입니다. DAG를 Python 코드로 관리하고 테스트할 수 있고, 재시도·의존성 기반 병렬 실행·XCom을 설정만으로 씁니다. api-server, scheduler, dag-processor로 역할이 나뉜 3.x 구성입니다.

Chapter 03

전체 구성

기능

  • ETF 탐색 — 검색, 테마 태그·액티브/패시브 필터, 상세(보유종목, 유사 ETF, 가격)
  • 액티브 ETF 비중 변화 — 액티브 ETF가 종목 비중을 어떻게 바꿨는지 날짜별로
  • 구성종목 분석 — ETF와 투자 비중을 넣으면 실제로 담기는 종목 비중을 계산
  • 포트폴리오 — 매수 기록, 목표 비중, 일별 스냅샷 대시보드, 공유
  • AI 챗봇 — 자연어 질문에 표·차트·해설로 답하는 화면
  • 관리자 — 챗봇 로그 검수, 화면 설계 예시, ETF 태그, 알림 설정

구성 요소

  • db — PostgreSQL 18 + Apache AGE + pgvector + pg_trgm
  • backend — FastAPI + pydantic-ai
  • frontend — React + TypeScript + Vite, nginx가 정적 파일을 서빙하고 /api를 백엔드로 넘김
  • airflow — 3.x, 수집·태깅 DAG

모두 Docker Compose로 띄웁니다. 외부에 열린 포트는 프런트엔드 하나이고, 백엔드·DB·Airflow는 내부에만 바인딩합니다. 가입은 초대 링크로 하고, 처음 만든 계정이 관리자가 됩니다.

하나의 PostgreSQL에서 CRUD는 관계형, 관계 탐색은 그래프, 예시 검색은 벡터로 나눕니다. 이 분리를 한 DB 안에서 할 수 있다는 것이 AGE를 고른 가장 큰 이유입니다.
Chapter 04

데이터 수집 — KIS Open API & Airflow

KIS에서 받는 것

  • ETF 목록 — 공개 종목 마스터 파일 (인증 불필요)
  • ETF 현재가 — NAV, 순자산, 상장주식수, 액티브/패시브 분류
  • 일봉 — ETF·주식 가격과 영업일 목록
  • ETF 구성종목 — 보유종목과 비중
  • 휴장일 — 개장 여부

총보수는 KIS가 주지 않아 네이버 증권에서, 포트폴리오의 장중 현재가는 yfinance에서 받습니다.

유니버스 — 190개 ETF

레버리지·인버스·선물·합성·커버드콜, 채권·원자재·통화·리츠·해외 투자 ETF를 이름으로 거르고, 순자산 500억 원 이상만 남깁니다. 한 번 들어온 ETF는 빠지지 않고, 운용사는 이름 앞 브랜드(KODEX, TIGER…)로 연결합니다.

수집 원칙

  • 백필하지 않는다 — 구성종목 API에 날짜 지정이 없어 과거 보유종목은 얻을 수 없습니다. 첫 실행부터 하루씩 쌓습니다
  • 가격은 확정된 날까지만 — 장중에는 미완성 일봉이 오므로 16시 전이면 전날까지만 받습니다
  • 구성종목은 개장일에, 공시된 날짜로 — KIS는 개장일 아침 08:30에 그날의 구성(직전 거래일 장 마감 기준)을 공시합니다. 개장일에만 받고 그날 날짜로 저장하며, 변화는 ETF별 직전 수집일과 비교합니다
  • 구성종목은 상위 30개 — API가 비중 상위 30개만 줍니다. 질의용 데이터라 그대로 쓰고, 전체 종목 수는 따로 표시합니다

DAG

  • rdb_sync_metadata (매일 08:40) — 종목 마스터 → 관계형 ETF 목록
  • age_sync_universe (매일 08:50) — 영업일 → 유니버스·가격 → 구성종목 → 주식 가격 → 수익률 → 액티브 ETF 비중 변화 → 신규 ETF 태깅 → 수집 기록·Discord 알림
  • rdb_realtime_prices (평일 장중 10분마다) — 보유 티커 현재가 → 포트폴리오 스냅샷
  • age_tagging (토 03:00) — 테마 태깅
  • embed_code_examples (수동) — 챗봇 예시 임베딩

모든 쓰기는 같은 날짜로 다시 돌려도 결과가 같게 만들었고, 조회에 실패한 ETF는 이전 값을 유지합니다.

Chapter 05

그래프 모델과 활용

etf_graph

  • CURRENT_HOLDS {date, weight} — ETF별 현재 보유종목(최대 30개). 수집할 때마다 교체하고, 현재 구성 조회는 모두 이것을 씁니다
  • HOLDS {date, weight} — 날짜별 보유 이력. 비중 변화를 비교할 때만 씁니다
  • HAS_PRICE — ETF와 종목 모두 날짜별 Price 노드로 가격을 가집니다

이력은 하루 약 4,100개씩 늘어납니다. "현재 보유종목"을 이력에서 매번 찾으면 데이터가 쌓일수록 느려지므로, 현재와 이력을 다른 관계로 나눴습니다. 현재 조회는 ETF당 30개 이하의 엣지만 읽습니다.

유사 ETF

공통 보유종목마다 두 비중 중 작은 값을 더하고, 기준 ETF의 비중 합으로 나눠 정규화합니다. 상위 30개만 있어 비중 합이 100%가 아니기 때문입니다.

MATCH (e1:ETF {code: $code})-[h1:CURRENT_HOLDS]->(s:Stock)
      <-[h2:CURRENT_HOLDS]-(e2:ETF)
WHERE e1 <> e2
WITH e2, COUNT(s) AS overlap,
     SUM(CASE WHEN h1.weight < h2.weight
         THEN h1.weight ELSE h2.weight END) AS similarity
RETURN {code: e2.code, name: e2.name, similarity: similarity}
ORDER BY similarity DESC LIMIT 5

관계형이면 자기 조인과 집계가 얽힐 쿼리가 MATCH 패턴 하나로 읽힙니다.

액티브 ETF 비중 변화

수집이 끝나면 Airflow가 모든 액티브 ETF를 직전 수집일과 비교해 신규 편입·편출·비중 증감을 계산하고 한 테이블에 저장합니다. 웹의 비중 변화 화면, 메뉴 배지, Discord 알림이 모두 이 결과를 읽으므로 서로 다른 숫자가 나오지 않습니다. 알림 기준(%p)은 관리자 페이지에서 정하고 읽을 때 적용합니다.

Chapter 06

ETF 테마 태깅

반도체, AI, 2차전지, 방산, 고배당 같은 태그 27개를 씁니다. 순서대로 붙입니다.

  • 지수 규칙 — "200", "코스피", "코스닥" 같은 이름 패턴으로 코스피/코스닥
  • 키워드 규칙 — 이름에 "반도체", "배터리", "원자력" 등이 있으면 그 태그
  • LLM 분류 — 나머지는 이름과 상위 보유종목을 근거로 LLM이 구조화된 출력으로 고릅니다. 맞는 테마가 없으면 붙이지 않습니다

LLM 결과는 실행마다 달라질 수 있어, 한 번 붙인 태그는 고정하고 새로 들어온 ETF만 태깅합니다. 전체 재태깅은 명시적으로 요청할 때만 합니다.

관리자가 직접 지정한 태그는 자동 태깅이 건드리지 않습니다. 사람의 판단에 가까운 "우량주"는 수동으로만 붙습니다.

Chapter 07

AI 챗봇 — 답을 화면으로

챗봇은 글로만 답하지 않습니다. 질문을 보고 화면을 먼저 설계하고, 화면의 각 영역을 스킬이 채웁니다. 자세한 흐름은 Architecture 페이지에 있습니다.

처리 순서

  • 질문 재작성 — 이전 대화가 있으면 "이거 구성종목은?"을 독립된 질문으로
  • 화면 설계 — Planner(LLM)가 화면을 줄과 슬롯으로 나누고, 슬롯마다 스킬·표시 방식·인자를 정합니다. 비슷한 질문의 설계 예시를 참고합니다
  • 슬롯 채우기 — 데이터 스킬이 그래프를 조회해 표·차트 데이터를 만듭니다. 서로 독립된 슬롯은 동시에 돌고, 끝나는 대로 화면에 나타납니다
  • 해설 — 마지막 슬롯이 앞 영역의 요약만 보고 해설을 흘려보냅니다

숫자는 LLM을 거치지 않는다

표와 차트의 숫자는 DB에서 곧바로 옵니다. LLM은 화면 설계와 해설만 하고, 해설에는 단위를 붙인 짧은 요약만 넘어갑니다. 그래서 숫자를 지어낼 틈이 없고, 일반 질문은 7~10초 안에 답합니다.

스킬로 안 되는 질문 — agent

스킬로 표현할 수 없는 질문은 agent 슬롯 하나로 넘깁니다. 안에서는 도구 10개를 가진 tool-calling 에이전트가 돌고, 그중 graph_query는 LLM이 쓴 Cypher를 직접 실행합니다.

  • 읽기 전용 트랜잭션, 실행 시간 10초 제한, SQL 따옴표를 탈출할 수 있는 $$·; 거부
  • pgvector로 비슷한 질문의 Cypher 패턴 예시를 찾아 프롬프트에 넣습니다. 고유명사는 자리표시자로 일반화해 엉뚱한 예시가 걸리지 않게 합니다
  • 어떤 도구를 어떤 인자로 불렀는지 화면에 단계별로 보여 줍니다
대상이 애매하면("반도체 ETF 구성종목") 하나를 추측하지 않고 후보를 보여 주며 되묻습니다. 관리자가 검수한 대화와 설계 예시가 다시 챗봇의 참고 자료가 됩니다.
Chapter 08

포트폴리오 관리 & 대시보드

사용자가 ETF와 주식의 매수 기록을 입력하면 현재가로 평가액을 계산하고, 목표 비중과의 차이로 리밸런싱을 보여 줍니다. 보유 수량·평균 단가·스냅샷 금액은 앱에서 AES-256-GCM으로 암호화해 저장합니다.

장중 10분마다 가격을 받은 직후 포트폴리오별 일별 스냅샷을 갱신하고, 대시보드는 그 추이를 그립니다. 포트폴리오는 다른 사용자에게 공유할 수 있습니다.

포트폴리오는 관계형 테이블을 씁니다. CRUD와 트랜잭션 중심 데이터는 관계형, 관계 탐색은 그래프라는 분리를 그대로 따릅니다.
Chapter 09

만들며 정한 원칙

날짜를 정확히

"데이터가 없음"과 "값이 0"은 다르고, "요청한 날짜"와 "데이터의 날짜"도 다릅니다. 새 데이터가 없으면 기존 값을 건드리지 않고, 저장 날짜는 API가 돌려준 실제 날짜와 공시일을 씁니다. 모든 쓰기는 다시 돌려도 결과가 같아야 합니다.

현재와 이력은 따로

같은 관계라도 "지금"을 묻는 조회와 "변화"를 묻는 조회는 저장을 나눕니다(CURRENT_HOLDS / HOLDS).

저장소는 조회하는 곳에 맞춘다

그래프

  • ETF-종목 보유, 유사 ETF, 태그
  • 날짜별 보유 비중과 가격
  • 챗봇이 조회하는 모든 것

관계형

  • 사용자, 포트폴리오, 매수 기록
  • 스냅샷, 챗봇 로그, 비중 변화
  • 트랜잭션이 중요한 데이터

LLM은 결정적이지 않다

숫자는 LLM 밖에서 만들고, 한 번 정한 결과(태그)는 고정하며, 사람이 정한 값이 자동 결과보다 우선합니다. LLM이 쓴 쿼리는 금지어 목록 대신 DB가 쓰기를 거부하게 막습니다.

새는 것을 드러낸다

이름 기반 필터는 편리하지만 규칙에 없는 이름은 조용히 새어 나갑니다. 운용사 "기타", 미분류 태그처럼 새는 것을 보여 주는 지표를 주기적으로 확인합니다.

Chapter 10

회고 & 마무리

Apache AGE

Good

PostgreSQL 하나로 관계형 + 그래프 + 벡터를 운영하고, PostgreSQL 도구를 그대로 씁니다.

Bad

Cypher 지원이 불완전하고 자료가 적습니다. 쿼리를 SQL 따옴표 안에 넣는 구조라 외부 입력에 신경 쓸 게 많습니다.

Recommend

이미 PostgreSQL을 쓰고 있고 그래프 쿼리가 워크로드의 일부일 때.

pydantic-ai

Good

가볍고 OpenAI 호환 엔드포인트에 바로 붙습니다. 도구 인자와 구조화된 출력을 스키마로 검증하고, 틀리면 모델에 되돌려 고치게 합니다.

Bad
